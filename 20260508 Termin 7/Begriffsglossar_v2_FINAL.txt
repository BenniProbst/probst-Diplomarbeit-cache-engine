[KANON]  KNOTEN (Node)
  SYN ← "Node"             ART [Leis 2013] · HOT [Binna 2018] · B²-tree [Schmeisser 2022] · START [Fent 2020] · Masstree [Mao 2012]
  SYN ← "Vertex"           Graphentheorie (allgemein)
  SYN ← "Decision Node"    B²-tree [Schmeisser 2022]: byte-weise Verzweigungsknoten
  SYN ← "Span Node"        B²-tree [Schmeisser 2022]: gemeinsame-Praefix-Knoten
  SYN ← "Trie Node"        Jacobson [1989] (allgemein): Knoten in succinct Encoding
  SYN ← "Internal Node"    Masstree [Mao 2012]: Nicht-Blatt-B+-Tree-Knoten
  SYN ← "Border Node"      Masstree [Mao 2012]: Knoten an Trie-Layer-Grenze
  SYN ← "Macro-Node"       CoCo-trie [Boffa 2024]: kollabierter Subtrie als Einheit
  BED Eine logische Verzweigungseinheit der Suchstruktur. Konsumiert i.d.R.
      einen Teil des Schluessels (Bit/Byte/Slice) und gibt einen oder mehrere
      Folgepointer/Folgeposition zurueck.
  ABG NICHT "Page" (eine Page kann mehrere Knoten enthalten) ·
      NICHT "Cache Line" (Hardware-Granularitaet) ·
      NICHT "Block" im Bender-Sinn (das ist eine Cache-Ebene-Block)

[KANON]  SEITE / PAGE
  SYN ← "Page"            B+-Tree, B²-tree [Schmeisser 2022], Masstree [Mao 2012]
  SYN ← "Block"           Bender/Demaine/Farach-Colton [2002] (Block in Multilevel Memory)
  SYN ← "Block"           Saikkonen/Soisalon-Soininen [2008] (Cache-Block)
  SYN ← "Suchseite"       PRT-ART Termin 1+
  SYN ← "Page-Cluster"    CSB+-tree [Rao/Ross 2000]: kontigous Sibling-Anordnung
  SYN ← "Disk Block"      klassische DBMS-Sicht
  BED Containereinheit, in der ein oder mehrere Knoten gespeichert und aus
      dem Cache/Speicher als Einheit geladen werden.
  ABG NICHT "Cache Line" (kleinere Granularitaet, Hardware-Einheit, 64 B);
      Page = Software-Konzept, Cache Line = Hardware.
  LIT Klassisch: B+-Tree-Literatur. PRT-ART verwendet "Page" als
      Software-Layout-Einheit, die mehrere Cache-Lines umfassen kann.

[KANON]  SEITENTYP / PAGE TYPE
  SYN ← "Page Type"        PRT-ART Termin 1+
  SYN ← "Node Family"      ART [Leis 2013]: Node4/16/48/256
  SYN ← "Node Layout"      HOT [Binna 2018], B-Trees Are Back [Mueller 2025]
  SYN ← "Encoding"         CoCo-trie [Boffa 2024]: Pool unterschiedlicher Encodings
  SYN ← "Page Format"      B²-tree [Schmeisser 2022]
  SYN ← "Multibyte Node"   START [Fent 2020]
  SYN ← "Adaptive Layout"  B-Trees Are Back [Mueller 2025]: Runtime-Layoutwahl
  SYN ← "Macro-Node Encoding" CoCo-trie [Boffa 2024]
  BED Konkrete Auspraegung einer Seite mit fester Layout-Konvention.
  PRT-ART FAMILIE (T2 eingefroren):
      • Dense-Byte-Page          ← analog ART Node256, dichte Byte-Transitionen
      • Extended Dense Page      ← analog START multilevel Nodes (mehrbyteig)
      • Sparse Patricia Page     ← analog HOT, diskriminierende Bits, sparse
      • Redirect-Page            ← analog CoCo-trie collapsed macro-nodes
      • PRT-Custom-Cache-Page    ← Eigener Beitrag (B²-tree + CSS/CSB+ Schnitt)

[KANON]  PFAD / SUCHPFAD
  SYN ← "Search Path"          allgemein
  SYN ← "Root-to-Leaf Path"    Bender/Demaine/Farach-Colton [2002]
  SYN ← "Traversal"            allgemein
  SYN ← "Lookup Path"          CoCo-trie [Boffa 2024], ART [Leis 2013]
  SYN ← "Hot Path"             Dortmund DAMON 2023 [Kuehn et al.]
  SYN ← "Frequent Access Path" Path-Prefetching FGCS 2024 [Zhang et al.]
  BED Sequenz von Knotenbesuchen vom Root bis zum Treffer/Miss.
      "Hot Path" = Pfad mit hoher Zugriffsfrequenz (Zielobjekt fuer Optimierung).

[KANON]  PRAEFIXKOMPRESSION
  SYN ← "Path Compression"      ART [Leis 2013]
  SYN ← "Lazy Expansion"        ART [Leis 2013]: Knoten erst materialisieren bei Verzweigung
  SYN ← "Patricia Bits"         HOT [Binna 2018], Patricia Tries (allgemein)
  SYN ← "Discriminative Bits"   HOT [Binna 2018]: pro Knoten dynamisch waehlbar
  SYN ← "Span"                  HOT [Binna 2018], B²-tree [Schmeisser 2022]: Bit-/Byte-Span pro Node
  SYN ← "Prefix Truncation"     B-Trees Are Back [Mueller 2025]
  SYN ← "Subtrie Collapse"      CoCo-trie [Boffa 2024]
  BED Eindeutige Schluesselsegmente werden NICHT als separate Knoten
      gespeichert, sondern in einem einzigen Knoten/Eintrag kondensiert.
  ABG REDIRECT (siehe naechster Eintrag) ist die PRT-ART-spezifische
      physische Umsetzung dieser logischen Idee.

[KANON]  REDIRECT
  SYN ← "Macro-Node"           CoCo-trie [Boffa 2024]: mehrere Subtrie-Ebenen kondensiert

  SYN ← "Jump Pointer"         Path-Prefetching FGCS 2024 [Zhang et al.]

[KANON]  FANOUT

[KANON]  HOEHE / TIEFE

1.5  SUCCINCT/SPACE-EFFICIENT FAMILIE (NEU mit Jacobson + SuRF integriert)
================================================================================

[KANON]  SUCCINCT TREE-ENCODING
  SYN ← "Succinct Tree"       Jacobson [1989] (LOUDS), Information Theory
  SYN ← "Space-efficient Tree" Jacobson [1989]: Titel
  SYN ← "Compact Tree"        allgemein
  SYN ← "Implicit Encoding"   Jacobson [1989]
  BED Tree-Repraesentation mit ~Information-theoretical Lower Bound bits/Knoten
      (~2 bits/node fuer bin Tree, ~10 bits/node fuer SuRF FST).
  ABG NICHT "compressed" (allgemein); succinct = nahe theor. Lower Bound,
      compressed = nur kleiner als trivial.

[KANON]  LOUDS-ENCODING (Level-Ordered Unary Degree Sequence)
  SYN ← "LOUDS"              Jacobson [1989]: Originalterm
  SYN ← "Level-Order Bit-String" Jacobson [1989]
  SYN ← "Unary Degree Sequence" Jacobson [1989]
  BED Bit-Sequenz Form 1*0 pro Knoten (degree-Bits + Terminator), Knoten
      in BFS-Reihenfolge. Ermoeglicht O(1)-Navigation via rank/select.
  PRT-ART Bezug:
      Konzeptionell aequivalent zu PRT-ART **Dense-Byte-Page** (oberhalb
      von Cache-Engine-Wahl) — succinct-codiert, statisch, aber sehr
      dense. PRT-ART braucht aber UPDATE-FAEHIGKEIT (LOUDS ist statisch).

[KANON]  LOUDS-DENSE
  SYN ← "LOUDS-Dense"         SuRF [Zhang 2018]
  SYN ← "D-Labels / D-HasChild / D-IsPrefixKey" SuRF [Zhang 2018]: 3 Bitmaps a 256
  BED SuRF Top-Levels Encoding: 3 Bitmaps der Groesse 256 (eine pro 256er-
      Verzweigungs-Byte) + Byte-Sequence fuer Werte. Cache-friendly.
  PRT-ART Bezug:
      **DIREKT mappbar auf PRT-ART Dense-Byte-Page!**
      Wenn PRT-ART eine succinct Page fuer dichte Subtries braucht:
      LOUDS-Dense waere die kanonische Struktur.

[KANON]  LOUDS-SPARSE
  SYN ← "LOUDS-Sparse"        SuRF [Zhang 2018]
  SYN ← "S-Labels / S-HasChild / S-LOUDS" SuRF [Zhang 2018]: byte-bit-bit pro Knoten
  BED SuRF Bottom-Levels Encoding: 3 Byte-Sequenzen, eine pro Trie-Knoten.
      Space-efficient, aber teurer Lookup.
  PRT-ART Bezug:
      **DIREKT mappbar auf PRT-ART Sparse Patricia Page!**
      LOUDS-Sparse = succinct sparse Repraesentation (vs HOT = byte-aligned
      sparse Repraesentation).

[KANON]  LOUDS-DS (Hybrid)
  SYN ← "LOUDS-DS"            SuRF [Zhang 2018]
  SYN ← "Hybrid Encoding"     SuRF [Zhang 2018]
  SYN ← "Cutoff Level R"      SuRF [Zhang 2018]: Schwelle Dense vs Sparse
  BED Kombination: Top-Levels in LOUDS-Dense (cache-friendly), Bottom-Levels
      in LOUDS-Sparse (space-efficient). Schwelle R tunable (default 64).
  PRT-ART Bezug:
      **HOECHST RELEVANT** — diese Hybrid-Logik ist KONZEPTIONELL
      AEQUIVALENT zu PRT-ART **Cache-Engine Page-Type-Selection Rules**!
      SuRF macht es STATISCH (Schwelle einmal beim Build); PRT-ART macht
      es DYNAMISCH (Cache-Engine entscheidet runtime).

[KANON]  RANK / SELECT
  SYN ← "rank"                Jacobson [1989], SuRF [Zhang 2018]
  SYN ← "select"              Jacobson [1989], SuRF [Zhang 2018]
  BED rank(i) = #1-Bits in Position [0..i] · select(j) = Position des j-ten 1-Bits.
      O(1) mit Vorberechnung; Grundoperation fuer succinct-Navigation.
  PRT-ART Bezug:
      Falls PRT-ART eine succinct Page einsetzt, brauchen wir eine
      rank/select-Implementierung. (Externe Lib z.B. SDSL.)

GESCHAERFTE DOMAENEN-TRENNUNG (FUER PHASE 3.D)
================================================================================

DOMAENE 1 — SUCH-ALGORITHMEN-DOMAENE
   Verantwortlich fuer:
      - Lookup-Semantik (Exact, Prefix, Range, Range-Filter)
      - Schluesselrepraesentation (plain bytes; optionale Fingerprints)
      - Ordnungsmodus (unsorted/local/lex)
      - Pflichtoperationen (CRUD)
      - Concurrency-Garantien (single/multi-reader, Updates)

   Modul-Bausteine:
      - Trie-Engine (globale Struktur, Redirect, Knoten-/Seitennavigation)
      - Knoten-/Seitentyp-Implementierungen (5 Typen, jede ein Modul)
      - ValueHandle-Mechanik (Inline/External/ChainRef)
      - Operation-Dispatcher (Get/Put/Delete/Range)

   "Cache-Engine SIEHT nicht IN die Knoten" — kennt nur Header-Telemetrie.

DOMAENE 2 — CACHE-ENGINE-DOMAENE
   Verantwortlich fuer:
      - Seitentyp-Auswahl (Page-Type-Selection Rules)
      - Prefetch-Policy (Distanz, Locality-Hints, an/aus)
      - Online-Relocation (wann, wo, wie)
      - Allocator-Steuerung (Pool/Arena pro Seitentyp)
      - Plattform-Kalibrierung (Modus 1/2/3)
      - Telemetrie-Erfassung (Probability Sketches, Read Counter)

   Modul-Bausteine:
      - Plattform-Profiler (Working Set, Stride, Prefetch-Distanz Sweeps)
      - Cost Model (anhand Plattform-Profil + lokaler Telemetrie)
      - Page-Type-Scheduler
      - Prefetch-Controller
      - Relocation-Manager
      - Allocator-Manager

   "Such-Algorithmus SIEHT nicht IN die Cache-Engine" — ruft nur
   Schnittstelle "such mir den Naechsten Knoten an Pfad x" auf.

DOMAENE 3 — MESS-/TELEMETRIE-DOMAENE (Querschnitt)
   Verantwortlich fuer:
      - Counter-Erfassung via perf/PAPI/Advisor
      - Histogramm-Ablage (HDR)
      - Plattform-Erkennung (CPU-Features, ISA, Cache-Hierarchie)
      - Reproduzierbarkeit (Seeds, Warmups, Pinning, Compiler-Flags)

   Modul-Bausteine:
      - Counter-Collector (perf/PAPI/Advisor Wrapper)
      - Histogram-Aggregator
      - Platform-Probe (CPU-ID, ISA-Detection, Cache-Topo)
      - Run-Recorder (Run-Logs mit Build-/Compiler-/Flag-Info)

   Wichtig: KEINE Mittelung von Perzentilen; 5 Laeufe je Konfiguration roh.

GEMEINSAMER VERTRAG (Schnittstelle Domaene 1 ↔ Domaene 2)
   - Cache-Engine sieht "Knoten/Pages" als opake Blobs mit
     Header-Telemetrie (Probability Sketches, Counter, Densitaet, Fanout).
   - Such-Algorithmen rufen auf: "Naechster Knoten unter Schluessel-Praefix x"
     und bekommen vom Cache-Engine-Modul den effektiven Seitentyp +
     Pointer/Handle zurueck.
   - **Single Direction Dependency**: Such-Engine darf Cache-Engine
     aufrufen; Cache-Engine darf NICHT in die Such-Logik greifen.

NICHT-MEHR-OFFENE PUNKTE (gegenueber Vorstufe)
================================================================================

Aus Begriffsglossar-Vorstufe waren folgende Punkte als TODO markiert.
Status nach REV4 + Phase 3.B + Phase 3.C:

* "ChainRef" (PRT-ART Termin 2 ValueHandle::ChainRef) — explizit vertagt;
   Bleibt vertagt (Termin 2 Entscheidung gilt). Mapping zu CoCo-trie Macro-Node
   ist NICHT direkt — Macro-Node ist eine Subtrie-Kollabierung, ChainRef ist
   eine Value-Verkettung. Konzeptionell unterschiedliche Domaenen.

* "fence" / "border node" (Masstree) vs. PRT-ART Page-Boundary —
   GEKLAERT: Masstree-Border-Node = PRT-ART Layer-Grenze (Slice-Wechsel).
   PRT-ART verwendet KEINE 8-Byte-Slices, daher keine direkte 1:1-Uebernahme.
   Konzeptionell aequivalent: Page-Boundary in PRT-ART trennt
   Trie-Huelle-Knoten von eingebetteter Such-Page-Logik.

* "Fingerprinting" (B-Trees Are Back) — Methodisch nah an Bloom-Filter,
   GEKLAERT: Fingerprinting = vorberechneter Hash-Bit-Vector pro Schluessel
   in der Page-Zeile. Reduziert teure String-Vergleiche.
   PRT-ART Termin 1: optional — nicht im Pflicht-Kern.

* "Heads / Hints" (B-Trees Are Back) — Mapping zu PRT-ART Probability Hints
   GEKLAERT: B-Trees-Are-Back "Heads" = Sortierte ersten Bytes der Schluessel
   in der Page-Header-Region (fuer schnellen Vergleich). NICHT identisch zu
   PRT-ART Probability Hints (statistische Telemetrie). Verschiedene Konzepte.

* "Concurrency Token" / "Version" (ART OLC, Masstree) vs. RCU Grace Period —
   GEKLAERT: OLC-Version = atomarer Counter pro Knoten (Lese-Pruefung).
   RCU-Grace-Period = globale Wait-fuer-alle-Reader-Mechanik.
   Komplementaer: OLC fuer Lookups, RCU fuer Memory Reclamation nach Relocation.
   PRT-ART nutzt im Kern beide (T4 Designentscheidung).

* SuRF "Fast Succinct Trie (FST)" + "LOUDS-Dense / LOUDS-Sparse" —
   VOLL INTEGRIERT in v2 (siehe 1.5 Succinct/Space-efficient Familie).
   LOUDS-Dense ↔ PRT-ART Dense-Byte-Page (Konzept aequivalent)
   LOUDS-Sparse ↔ PRT-ART Sparse Patricia Page (Konzept aequivalent)
   LOUDS-DS Hybrid ↔ PRT-ART Cache-Engine Page-Type-Selection (Konzept aequivalent)
   ABER: SuRF ist STATISCH; PRT-ART braucht Updates -> wir koennen LOUDS-Encoding
   nicht 1:1 uebernehmen, sondern nur als konzeptionelle Inspiration nutzen.
