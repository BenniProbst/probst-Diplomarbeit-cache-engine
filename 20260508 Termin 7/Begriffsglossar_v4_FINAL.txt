[KANON]  CACHE ENGINE (Top-Level-Definition, KORRIGIERT)
  SYN ← "Cache-Engine"            PRT-ART Termin 2-6 + Termin 7 (KANON)
  SYN ← "Cache Control Plane"     PRT-ART Termin 5
  SYN ← "Active Cache Layer"      PRT-ART Termin 4
  SYN ← "Meta-Ebene"              PRT-ART Termin 5
  SYN ← "Live CPU-Modell"         PRT-ART Termin 7 REV 2
  BED Globales Heap-Modul (Singleton-aehnlich), das ein laufendes Modell
      der CPU bereitstellt. Per Definition: Modell der CPU, ihrer
      Eigenschaften, Prozesse/Ablaeufe und Verarbeitungs-Bewusstsein,
      um Verarbeitungseigenschaften mit wissenden Entscheidungen ueber
      die Architektur zu verbessern.
  STRUKTUR Zwei Funktionsschichten:
      • Schicht A — COMPILE TIME: separates Programm `CacheEngineBuilder`

      • Schicht B — RUNTIME: globales Heap-Modul `CacheEngineRuntime`,

  KORREKTUR vs v3: in v3 als monolithische Meta-Ebene beschrieben — in v4
      explizit zweischichtig (Compile-Time-Programm + Runtime-Singleton).

[KANON]  STATIC ENGINE
  BED Engine-Variante, die exakt den Originalcode eines Algorithmus liefert
      und KEINE Optimierungen ueber den State-of-the-Art hinaus vornimmt.
      Implementiert die std::map-API als Top-Level-Adapter.
  EINSATZ Vergleichsbasis fuer CacheEngine-Messungen.
  BEZ `template<typename Algo> StaticEngine<Algo>`

[KANON]  ENGINE-CHOICE
  BED Compile-Time-Wahl zwischen StaticEngine und CacheEngine via Template-
      Parameter. KEIN Runtime-Switching.
  BEZ `template<typename Algo, typename EngineKind> Container<Algo, EngineKind>`

[KANON]  OBSERVER PATTERN  (im Cache-Engine-Kontext)
  SYN ← "Observer"                  GoF Design Patterns
  SYN ← "Publish/Subscribe"         allgemein
  SYN ← "Notification Sink"         PRT-ART Termin 7 REV 2
  BED Such-Algorithmus benachrichtigt CacheEngineRuntime ueber Ereignisse
      (PageAccessed, NodeAccessed, PathTraversed, TelemetryUpdate,
      MutationCommitted). CacheEngineRuntime hostet die Observer-Registry.
  RICHTUNG Algorithmus → CacheEngine

[KANON]  VISITOR PATTERN  (im Cache-Engine-Kontext)
  SYN ← "Visitor"                   GoF Design Patterns
  SYN ← "Double Dispatch"           allgemein
  BED CacheEngineRuntime besucht Algorithmus-Strukturen (Page, Node,
      Traversal) ueber Concept-Interfaces, OHNE algorithmus-spezifische
      Internals zu kennen. Algorithmus implementiert `accept(visitor)`.
  RICHTUNG CacheEngine → Algorithmus

[KANON]  STRATEGY PATTERN  (Algorithmus-Wahl)
  SYN ← "Strategy"                  GoF Design Patterns
  BED Jeder Such-Algorithmus (P01-P33 + PRT-ART) ist eine konkrete
      `IAlgorithmStrategy<K,V>`-Implementierung. Container kapselt eine
      Strategy als Template-Parameter.

[KANON]  ADAPTER PATTERN  (Originalcode-Anbindung — HABICH-DIREKTIVE)
  SYN ← "Adapter"                   GoF Design Patterns
  SYN ← "Wrapper"                   allgemein
  BED Originalcode der Paper liegt unveraendert unter `ext/<paper>/`. Ein
      Adapter pro Algorithmus uebersetzt zwischen Original-API und unseren
      C++23-Concepts (FanOutContainer, Page, Node, Traversal, ...).
  REGEL siehe BLOCK J (Habich-Direktive).

[KANON]  SINGLETON  (CacheEngineRuntime + ConcurrencyManager)
  SYN ← "Singleton"                 GoF Design Patterns
  SYN ← "Globales Modul"            PRT-ART Termin 7 REV 2
  BED Genau eine Instanz pro Prozess; Lebenszeit = Programm-Lebenszeit;
      Heap-allokiert mit deterministischer Zerstoerung am Programm-Ende.
  ANWENDUNG `CacheEngineRuntime::instance()`,
            `ConcurrencyManager::instance()` (lebt IN der CacheEngineRuntime)

BLOCK B — CACHE-ENGINE-SPALTUNG (BUILDER vs RUNTIME)
================================================================================

[KANON]  CACHE ENGINE BUILDER  (Compile-Time-Programm)
  BED Eigenstaendiges C++23-Programm, das die moeglichen Rekombinationen
      verschiedener Such-Algorithmen + ihrer Bestandteile permutiert, jede
      Permutation per Metaprogrammierung statisch kompiliert + ausmisst,
      in eine Datenbank persistiert und am Ende einen LaTeX-Anhang fuer
      die Diplomarbeit rendert.
  EINSATZ `comdare-cache-engine-builder run --architecture <isa> --dataset <ds>`
  BESTANDTEILE PermutationEngine, ConstexprCodegen, CompilerDriver,
              BuilderMeasurement, MeasurementDB, LatexRenderer

[KANON]  CACHE ENGINE RUNTIME  (Runtime-Modul, Heap, global)
  BED Globales Heap-Modul (Singleton-aehnlich), das per Observer Telemetrie
      empfaengt und per Visitor Algorithmus-Strukturen besucht. Empfiehlt
      Ausfuehrungsstrategien basierend auf Compile-Time-Wissen aus der DB.
      Hostet `LiveCpuModel`, `ConcurrencyManager`, `RuntimeMicroBenchmarks`,
      `CompileTimeKnowledge`, `TelemetrySpool`.

[KANON]  LIVE CPU-MODELL
  BED In-Process Modell der CPU + ihrer Topologie + ihrer aktuellen Last.
      Liefert CpuFeatures, MemoryTopology, LoadSnapshot, EstimatedMetric.
  EINSATZ Wird von der CacheEngineRuntime gehalten und von Visitor +
          Observer-Logik konsultiert.

[KANON]  COMPILE TIME KNOWLEDGE
  BED Snapshot der MeasurementDB, eingebettet als constexpr-Tabelle oder
      geladen aus DB beim Programmstart. Mappt (Architecture, Workload)
      auf StrategyRecommendation.

[KANON]  RUNTIME MICRO BENCHMARK
  BED Im Algorithmus-Lauf eingebettete Mikromessungen, deren Ergebnisse
      in_memory akkumuliert und am Ende gespoolt werden.
  ABG NICHT BuilderMeasurement (Compile-Time, statisch); RuntimeMicroBenchmark
      laeuft in der Engine zur Laufzeit.

[KANON]  TELEMETRY SPOOL
  BED Akkumulator fuer Telemetrie-Samples (lock-free Ring oder per-thread).
      Wird am Ende eines Laufs geflusht und kann optional in die
      MeasurementDB gemerged werden.

BLOCK E — std::map-API (BASISVERTRAG)  [Quelle: cppreference.com C++23]
================================================================================

[KANON]  std::map-API-VERTRAG
  BED Jeder Such-Algorithmus implementiert die vollstaendige `std::map<K,V>`-
      API (C++23). Algorithmen sind dropin-Ersatz fuer std::map. Der Key-Type
      kann implizit mit Hashing/Fingerprinting ueberlagert sein.
  QUELLE https://en.cppreference.com/cpp/container/map

OPERATIONEN (vollstaendig, mit Standard-Version)
  Construction / Destruction
   - map() / map(Compare) / map(InputIt, InputIt, Compare, Alloc)
   - map(const map&) / map(map&&) / map(initializer_list, Compare, Alloc)
   - map(from_range_t, R&& rng)                                  [C++23]
   - ~map()
  Assignment / Allocator
   - operator=(const map&) / operator=(map&&) / operator=(initializer_list)
   - get_allocator()
  Element Access
   - at(key) / operator[](key) / operator[](key&&)
  Iterators
   - begin() / cbegin() / end() / cend() / rbegin() / crbegin() / rend() / crend()
  Capacity
   - empty() / size() / max_size()
  Modifiers
   - clear()
   - insert(value_type) / insert(InputIt,InputIt) / insert(initializer_list)
   - insert_or_assign(K, V)                                      [C++17]
   - insert_range(R&&)                                           [C++23]
   - emplace(args...) / emplace_hint(hint, args...)
   - try_emplace(K, args...)                                     [C++17]
   - erase(iterator) / erase(K)
   - swap(map&)
   - extract(K) / extract(iterator)                              [C++17]
   - merge(map&)                                                 [C++17]
  Lookup
   - count(K) / find(K) / contains(K)                            [contains: C++20]
   - equal_range(K) / lower_bound(K) / upper_bound(K)
  Observers
   - key_comp() / value_comp()
  Non-member
   - operator==, operator<=>                                     [C++20]
   - erase_if(map&, Pred)                                        [C++20]
   - swap(map&, map&)
  Deduction Guides                                                [C++17]

[KANON]  TRANSPARENT COMPARE
  BED `Compare::is_transparent`-Marker erlaubt heterogene Lookup ohne
      Konstruktion eines Key-Objekts. Wichtig fuer effiziente Range-Queries
      und Praefix-Matches.

[KANON]  IMPLICIT KEY OVERLAY
  BED Key-Type kann implizit mit Hashing/Fingerprinting ueberlagert sein
      (z.B. ART/HOT bytewise; Bloom-Filter-Fingerprint pro Knoten).
      `template<typename K, typename Overlay = NoOverlay>`

BLOCK G — VALUEHANDLE  (KORRIGIERT vs v3)
================================================================================

[KANON]  VALUEHANDLE  (KORRIGIERT)
  KORREKTUR vs v3: ValueHandle ist NICHT eine globale Top-Level-Klasse,
      sondern eine Eigenschaft DER NODE. Compile-Time-`switch_array` begrenzt
      zulaessige Varianten je Algorithmus; Runtime waehlt je Knoten-Eigenschaft.
  BED Strategie zur Speicherung des Werts an einem terminalen Knoten.

[KANON]  VALUEHANDLE-KIND  (Enum, je Node konfigurierbar)
   • Inline           — Wert direkt im Node-Slot
   • Pointer          — External Pointer auf separates Werte-Array
   • RedirectToNode   — verweist auf naechste Node (Patricia-Style)
   • RedirectToPage   — verweist auf naechste Page
   • ChainRef         — VERTAGT (Wertekette)
   • Dynamic          — Runtime-Auswahl, mit `switch_array` begrenzt

[KANON]  VALUEHANDLE-SWITCH-ARRAY
  BED Compile-Time-`std::array<ValueHandleKind, N>`, das je Algorithmus die
      zulaessigen Varianten kodiert. Runtime waehlt aus dieser Menge.
  BEISPIELE (vorlaeufig):
   • ART:        Inline | Pointer | RedirectToNode
   • HOT:        Inline | Pointer
   • B²-tree:    Inline | Pointer | RedirectToPage
   • PRT-ART:    Inline | Pointer | RedirectToNode | RedirectToPage | Dynamic

[KANON]  DYNAMIC VALUEHANDLE
  BED Runtime-entscheidende Variante: pro Knoten zur Laufzeit Inline vs
      Pointer vs Redirect waehlen, basierend auf Knoten-Eigenschaften
      (Wertegroesse, Hot/Cold-Score, Pointer-Tiefe, ...).

BLOCK H — CONCURRENCY-MANAGER + DISZIPLINEN  (KORRIGIERT vs v3)
================================================================================

[KANON]  CONCURRENCY MANAGER  (Singleton in CacheEngineRuntime)
  BED Singleton, das die feingranulare Concurrency-Disziplin orchestriert.
      Jede Disziplin ist eine eigene Klasse.
  KORREKTUR vs v3: in v3 nur als grobe "Concurrency-Garantien"-Notiz —
      in v4 als 8+ benannte Disziplinen.

DISZIPLINEN
   1) PAGE CONCURRENCY        — Parallelitaet auf Suchseiten-Granularitaet
   2) NODE CONCURRENCY        — Parallelitaet auf Knoten-Granularitaet
   3) ARRAY CONCURRENCY       — intra-Knoten-Arrays (z.B. children[])
   4) DATA STRUCTURE CONC.    — gesamte Subtree-/Datenstruktur-Ebene
   5) PATH CONCURRENCY        — Parallelitaet entlang Suchpfade
   6) MEMORY ACCESS CONC.     — Lese-/Schreib-Parallelitaet
                                (nur read parallel; nur write parallel;
                                 read-write parallel — drei Sub-Disziplinen)
   7) SIMD THREAD CONC.       — SIMD-Parallelitaet IN bestimmten Threads
   8) SIMD FLOW CONC.         — SIMD-Parallelitaet IN bestimmten Thread-
                                 Ablaeufen (nicht der ganze Thread)
   (Erweiterbar: NumaConcurrency, EpochConcurrency, ...)

[KANON]  RCU-RECLAIM  (BLEIBT — Default fuer Online-Relocation)
  BED Read-Copy-Update; deterministisches Aufraeumen nach Grace Period.
  BELEG-LIT P29 McKenney2001

[KANON]  HAZARD POINTERS  (ENTFERNT vs v3)
  STATUS REMOVED in v4. Begruendung: memory leak ist verbotenes
      undefiniertes Verhalten; Aufraeumen ist Pflicht; deterministische
      Reclamation via RCU + EpochManager ist ausreichend; kein GPU-Code.
