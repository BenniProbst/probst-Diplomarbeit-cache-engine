### TODO V41.E11 — cache-engine als Master-Framework mit Facade + Abstract-Factory-Pruefling (User-Direktive 2026-05-25)
**User-Wortlaut 2026-05-25:**
> "Vielleicht können wir über Interfaces in der cache-engine die nun ausgelagerten submodule anbieten. Die cache-engine ist damit das master framework Modul des Frameworks. Die entstandenen Module können dann durch die Cache-Engine als Facade pattern verwendet werden, ohne dass die Diplomarbeit erneut diese Module laden muss. Weiterhin macht eine Struktur Sinn, in der das Permutationsmodul in der Cache-Engine einen Prüfling wie den prt-art als abstract factory pattern zusätzlich zu den eigenen Achsen aufnimmt und damit HAT die cache-engine per cmake konfigurierte Prüfling(e), welche durch eine Orchestration eines Messprojektes wie der Diplomarbeit ausgewertet und konfiguriert werden."

**Architektur-Vision:**
```
                    Master Framework
                    ┌──────────────────────────────────┐
                    │  comdare-cache-engine            │
                    │  ┌──────────────────────────┐    │
                    │  │ Facade: ICacheEngine     │    │
                    │  │   liefert search-engine, │    │
                    │  │   measurement,           │    │
                    │  │   isa-dispatch,          │    │
                    │  │   cache-engine-core,     │    │
                    │  │   build-tools,           │    │
                    │  │   test-system            │    │
                    │  └──────────────────────────┘    │
                    │                                   │
                    │  ┌──────────────────────────┐    │
                    │  │ PermutationModul         │    │
                    │  │   + AbstractFactory      │    │
                    │  │     Pruefling-Slot       │    │
                    │  │     (z.B. prt-art)       │    │
                    │  └──────────────────────────┘    │
                    │                                   │
                    │  HAT Pruefling(e) via CMake-Cfg  │
                    └──────────────────────────────────┘
                              ▲          ▲
                              │ uses     │ as test-subject
                    ┌─────────┴──┐   ┌───┴───────┐
                    │ Diplomarbeit│   │ prt-art   │
                    │ (Mess-      │   │ (Pruefling)│
                    │  Projekt)   │   │           │
                    │ orchestriert│   └───────────┘
                    │ + bewertet  │
                    └─────────────┘
```

**Konkret:**
1. **cache-engine** wird Master-Framework — vermittelt die 6 ausgelagerten Submodules NICHT als direkt-Includes/Linkings fuer Konsumenten, sondern via **Facade-Interfaces** (`ICacheEngine`, `IMeasurement`, `IIsaDispatch`, `ITestSystem`, ...).
2. **Diplomarbeit** linkt nur gegen cache-engine. Diplomarbeit ruft `cache_engine::measurement()` auf — cache-engine vermittelt intern an `comdare-measurement`-Modul. Diplomarbeit muss die Modul-Includes NICHT direkt sehen.
3. **PermutationModul** in cache-engine bekommt zusaetzlich zu Achsen-Slots einen **Pruefling-Slot** via Abstract Factory: `IPrueflingFactory`. Pruefling (z.B. prt-art) registriert sich beim Factory-Bootstrap.
4. **CMake-Konfiguration:** `COMDARE_CE_PRUEFLING=prt-art` haengt einen Pruefling an die cache-engine. Mehrere Prueflinge moeglich: `COMDARE_CE_PRUEFLING=prt-art;mein-zweiter-pruefling`.
5. **Diplomarbeit als Messprojekt** orchestriert + bewertet. Linkt nur cache-engine. Konfiguriert via CMake welche Prueflinge mit dabei sind.

**Konsequenzen fuer die aktuelle Architektur:**
- V41.E5 ist obsolet (Diplomarbeit linkt NICHT direkt gegen Mess-Modul — gibt vor cache-engine als Facade).

### TODO V41.E10 — STATIC/SHARED als pro-Projekt + pro-Untermodul-Achse (User-Direktive 2026-05-25)
**User-Wortlaut 2026-05-25:**
> "Derzeit kann ich nicht waehlen ob die Builds der Diplomarbeit als weitere ACHSE static oder shared gebaut werden. Das muss je Projekt einzeln und auch in der Diplomarbeit je Projekt-Untermodul eigenstaendig konfigurierbar sein. Fuer den Gesamtaufbau sind alle static gebaut als default, nur die Permutations-Binaries eines Algorithmus-Achsen-Gesamtaufbaus ist als statische binary per C++-23-Modul-.so dynamisch als Modul je Experiment in den CacheEngineBuilder zu laden, um ein Experiment auszufuehren, das gilt auch fuer Prueflings-Permutations-Algorithmen-Binaries wie den prt-art, welcher ebenfalls seine eigenen vollstaendigen prt-art binaries erzeugen muss, die dann als Experiment geprueft werden. shared wuerde Latenzen fuer das Laden einzelner Bestandteile eines Suchalgorithmus erzeugen was das Ergebnis verfaelscht -> verboten. Der Gesamt-Stack eines Experiment Algorithmus muss in seiner Gesamtheit als zusammenhaengende binary vorliegen. Ja das bedeutet zehntausende grosse Suchmodul-Binaries, was sehr sehr viel Speicherplatz kosten wird und das ist in Ordnung so."

**Begruendung (Mess-Praezision, parallel zur V41.A2.1-Direktive):**
Dynamic Loading einzelner Algorithmus-Bestandteile via `dlopen`/`LoadLibrary` zur Hot-Path-Zeit produziert Lade-Latenzen + zusaetzliche Cache-Misses + Symbol-Resolution-Overhead. Auf Zielsystemen mit ±0.1%-Praezision wuerden diese Effekte die echten Algorithmus-Unterschiede UEBERLAGERN. Wissenschaftlich publizierbare Messungen brauchen einen **Cold-Start-stabilen Gesamt-Stack pro Permutation** — alles im selben Memory-Image, kein dynamisches Nachladen.

**Soll-Architektur:**
1. **Default fuer alle Libraries:** STATIC (`add_library(<name> STATIC ...)`)
2. **Pro Projekt konfigurierbar:** Option `COMDARE_<PROJECT>_BUILD_SHARED_LIBS` (Default OFF)
3. **Pro Untermodul der Diplomarbeit konfigurierbar:** Option `COMDARE_DA_<MODULE>_BUILD_SHARED` (Default OFF) — fuer alle 6 Pipeline-Stages (01_sample_data_generator bis 06_latex_to_pdf) + 02_messung_driver
4. **Ausnahme Permutations-Binaries:** SHARED nach aussen (`.so`/`.dll`/`.dylib`) — als C++23-Module dynamisch ladbar in CacheEngineBuilder. **INTERN aber STATIC**: alle Achsen-Bestandteile (SIMD-Code-Pfad, Allokator-Library, Layout-Container, Algorithmus-Body) komplett in die perm_<id>.so/.dll einkompiliert. **NICHT** runtime-dlopen von z.B. mimalloc.dll oder einer cache_engine_core.so.
5. **Pro Pruefling (prt-art) gilt dasselbe:** perm_pa_<id>.so/.dll ist self-contained — alle prt-art-Algorithmus-Bestandteile statisch gelinkt.
6. **Gesamtmenge:** zehntausende grosse Binaries (medium/full Profile, pro Achsen-Kombination eine eigene self-contained .so/.dll). Speicherplatz-Verbrauch akzeptabel.

**Ist-Stand (V38.B+V40.A+V41.A2):**
- Permutations sind bereits SHARED (= dynamisch ladbar via Plugin-Loader V38.C) ✓
- Permutations linken mimalloc/snmalloc STATIC ein (vendor-static-libs) ✓
- ABER: cache-engine eigene libs (libs/cache_engine/*) sind meist STATIC, manche INTERFACE — kein expliziter Schalter
- ABER: keine projekt-uebergreifende STATIC/SHARED-Achse + keine pro-Untermodul-Konfiguration
- ABER: cache-engine FetchContent-libs (gtest) sind oft SHARED — Wahl nicht parameterisiert

### TODO V41.F.2 — Axen-zentrische Namespace-Restrukturierung
**User-Wortlaut:** "Wenn laut Plan nun die cache-engine Prüflinge wie prt-art als Command Pattern besitzt und ebenfalls ausführt, dann braucht es für die Wartbarkeit des codes auch die dazu passende namespace Struktur. Der prt-art muss als Prüfling die Strukturen (und wenn auch nur dummies) für jede Achse der cache-engine vorhalten, ist also je Axe eine Spezialimplementierung der Cache Engine interfaces für geänderte Achsen. Dies führt dazu, dass ein namespace etwa so aussehen sollte: comdare::cache_engine::<algorithm_axis>::optional_prt_art_impl . Unter comdare::cache_engine::<algorithm_axis> finden wir ALLE strukturieren Axen Interfaces bereits bestehender Implementierungen in der Bibliothek wie gehabt. Die comdare::cache_engine:: liefert tools, Werkzeuge und so weiter wie gehabt. Unter comdare::prt_art:: finden wir nur prt_art spezifische Hilfsimplementierungen."

**Soll-Namespace-Struktur:**
```
comdare::cache_engine::                      // Tools/Werkzeuge (zentral)
comdare::cache_engine::<algorithm_axis>::    // ALLE Axen-Interfaces aller Implementations
  comdare::cache_engine::simd::*             // Achse SIMD: Interface + bestehende Impls
  comdare::cache_engine::layout::*           // Achse Layout: ...
  comdare::cache_engine::alloc::*            // Achse Allokator: ...
  comdare::cache_engine::lookup::*           // Achse Lookup: ...
  comdare::cache_engine::node::*             // Achse Node: ...
  ... (alle 14 Axen mit Sub-Axen aus Bausteine-Matrix)
comdare::cache_engine::<axis>::optional_prt_art_impl  // Pruefling-Spezialisierung pro Achse
comdare::prt_art::                           // prt-art spezifische Hilfs-Implementations
```

**Implementations-Mechanismus (User-Wortlaut):**
> "Für gewöhnlich hat eine cache-engine Prüflinge, indem über ein dynamisches cmake include array einfach die list<<comdare::cache_engine::<algorithm_axis>::optional_prt_art_impl>...> namespaces von extern inkludiert und in die cache engine per compile registriert werden."

Konkret: CMake-Variable `COMDARE_CE_PRUEFLINGE` (Liste, z.B. `prt_art;mein_zweiter`). cache-engine durchlaeuft fuer jeden Pruefling alle Achsen, includiert `<comdare/cache_engine/<axis>/<pruefling>_impl.hpp>` falls vorhanden, registriert Compile-Time. Pruefling kann pro Achse leer (Dummy) oder echt sein.

**Migration:**
1. Headers reorganisieren: `cache_engine/indexes/linear_probe_hashset.hpp` → `cache_engine/axes/lookup/linear_probe_hashset.hpp`
2. Namespaces umbenennen: `comdare::cache_engine::indexes::*` → `comdare::cache_engine::lookup::*`
3. Pro Achse: ein abstract-base-Interface (z.B. `cache_engine/axes/lookup/i_lookup_strategy.hpp`)
4. Pruefling-Impls per CMake-Liste registriert: `cache_engine/axes/lookup/optional_prt_art_impl.hpp`
5. PermutationsModul vermittelt Achsen-Wahl

**Aufwand:** GROSS (Namespace-Migration aller bestehenden Komponenten). Verbunden mit V41.E11 (Facade-Pattern braucht klare Axen-Interfaces).
