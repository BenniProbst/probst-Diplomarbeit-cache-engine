## E17 — P/E-Core als dynamische Unter-Achse der Hardware-Systemachse

**Ist:** CPUID-Probe liest Leaf 0x1A heute NICHT (`cpuid_probe.hpp:55-73,163-171`; Hybrid-Flag 07H:EDX[15] ungelesen); Hybrid bewusst deaktiviert (`cpuid_platform_probe.hpp:38-39`). Andockpunkte da: `PlatformPropertySet.has_hybrid_cores/…/measured_metrics` (`i_platform_probe.hpp:14-24`), `CoreClass{HighIpc=P,LowIpc=E}` (`core_layout.hpp:14-19`, 0 Impl), `MeasurementSourceCaps.hybrid_core_aware` (`i_measurement_source.hpp:55`, nie gesetzt). **Realer Aktuator existiert:** `ScopedThreadPin` RAII via `sched_setaffinity` + `NoPinPolicy`/`CorePinPolicy` (Policy-Based, `thread_pinning.hpp:16-104`). CRTP-Wurzel: `SystemAxis<Derived>` (`system_axis.hpp:147-190`, empty-base, kein vtable).

**SOTA:** CPUID 0x1A ist inhärent LAUFZEIT (EAX[31:24]: 0x40=P/0x20=E des Kerns, auf dem es läuft → volle Karte nur per Pinnen+CPUID je logischem Prozessor → statische Compile-Time-Einrichtung sinnlos). Ab Meteor Lake 0x1A unzureichend → Linux sysfs `cpu_core`/`cpu_atom` + `cpu_capacity` autoritativ; perf misst pro Kern-Typ (PMU-Type-ID in `attr.config[63:32]`). Thread Director = dynamisch → für reproduzierbare Messung per Affinity-Pinning übersteuern.

**Design-Vorlage:** `HardwareSystemAxis<Derived>:SystemAxis<Derived>` (CRTP+Concept) mit compile-time-HAUPTACHSE = Host-Hardware-Identität (is_hybrid, SIMD, cache_line → Ordner/Label, NIE binary_id) + runtime-UNTER-Achsen `PeCorePolicySubAxis{Unpinned|PCoresOnly|ECoresOnly|HybridAware}` (Discovery CPUID.1AH→sysfs→hwloc; Aktuator ScopedThreadPin beim Setup; honest-0 auf Nicht-Hybrid) + NumaSubAxis + MultithreadingSubAxis. CSV-Spalten (dynamisch): `pe_policy` (config) + `ran_on_core_type` (beobachtet 0x40/0x20). Default Unpinned → 1 Pass, golden-neutral, kein Hot-Path-vtable (Pin einmalig cold-start).

**Forks (Gate):** **H-1 (Kern):** P/E unter Hardware (User-Wort) vs. Dossier-23-§2.4 P/E-Dispatch unter Scheduling. *Empf.: Hardware trägt das FAKTUM (Core-Typ-Karte + beobachteter ran_on_core_type), die aktive Pinning-POLICY als Scheduling-Unter-Achse — Doppel-Modellierung vermeiden; falls beides unter Hardware gewünscht, Scheduling entlasten.* **H-2:** G-270a geparkt → erst beobachtend (ran_on_core_type, Policy=Unpinned), aktives Pinning als Folge-Increment. **H-3:** Detektions-Kette CPUID→sysfs→hwloc (erster Treffer). **H-4:** CSV = pe_policy + ran_on_core_type (beide). **H-5:** Hybrid-PMU-Wahl (cpu_core/cpu_atom) hinter `hybrid_core_aware` als Folge-Increment.

## E18 — Set als eigene Gattung

**Ist (KERN-BEFUND): Set ist BEREITS ein vollständiges Genus (~90 % der Doktrin erfüllt).** 3-Ebenen (`anatomy_base.hpp`): Ebene-1 `AnatomyGattung`={SearchAlgorithm,Container,Graph} (nur 3, :40-44); Ebene-2 `AnatomyGenus`={SearchAlgorithm,Set,Sequence,Adapter,View} (:67-73); `gattung_of(Set)→Container` (:89-98). **Set hat:** `SetComposition<T0..T14>` (15 K-only-Achsen, ohne mapping/value_handle, `set_composition.hpp:14-38`), `SetAnatomy` (`set_anatomy.hpp:31-85`), **eigene ABI** `ISetTier`+`SetObserverSnapshotV1` (standard_layout+trivially_copyable, V1, `set_tier.hpp:17-61`), `SetAbiAdapter` (`static_assert genus()==Set`), **eigene** `GenusBindingTraits<Set>` (slot_count=15, `genus_binding_traits.hpp:85-105`), `SetDock`, Test `test_d9_set.cpp`. map = das SearchAlgorithm-Genus (kein separates map-Genus).

**Zwei Spannungen:** (1) **Level-Konflikt:** Code modelliert Set als Ebene-2-Genus UNTER Container; User-Doktrin „map/container=Sequence/Set = getrennte Gattungen" kollidiert mit dem eingefrorenen 3-Gattung-Modell (Doc 37 §5: kein Ebene-1-Eintrag außer User-GO; #29-GEPARKT ABI/golden-berührend). (2) **Semantik-Tiefe:** `SetAnatomy` = dünne K=V-Projektion über search_algo; fehlen native Set-Semantiken.

**C++-std-Set:** `std::set` (RB-Baum, O(log n), sortiert), `unordered_set` (Hash, O(1)~), `flat_set` (C++23, sortierter Vektor), multiset (Duplikate). Ops insert/erase/find/contains/count + **node_handle extract/merge** (C++17) + Mengen-Ops `set_union/intersection/difference` (`<algorithm>`, O(n+m)). Set vs map = eindeutige K≡V (degenerierte map); Set vs Sequence = Mitgliedschaft/positionslos vs. index-adressiert (non-intersecting type-erzwungen).

**Design-Vorlage (additiv, golden-neutral):** Set bleibt `Genus::Set` mit eigener ABI; native Ops via **V2-POD append-only** bzw. `ISetTierV2` (union/intersection/extract, default-OFF end-append); neue Achsen `ordering`(ordered/unordered/flat)+`multiplicity`(unique/multi) am Ende angehängt (Default=Ist → bit-identisch); Observer-Reuse via gemeinsamem Schwanz; mutual-use: Set-Organ INTERN = search_algo (node-set) / Sequence (flat_set) / Bucket-Array (hash_set), ohne Interface-Schnitt.

**Forks (Gate):** **F1 (Kern):** **F1a** User-„Gattung"≡Code-„Genus" → Set ist schon eigenes Genus+ABI+BindingTraits → nur Doku/Vokabular versöhnen, golden-neutral (*Empf.*) vs. **F1b** Ebene-1-Promotion `AnatomyGattung::Set` (bricht eingefrorene Enum + `container_framework::type_count` + alle `gattung==Container`-asserts → ABI/golden-GO; nur wenn die Direktive DAS meint). **F2:** dünne K=V behalten vs. native Set-ABI additiv. **F3:** ordering/multiplicity als Achsen-Werte end-append (*Empf. a*, golden-neutral) vs. je eigenes Genus (b, GO). **F4:** mutual-use-Backing bestätigen (search_algo/Sequence/Bucket ohne Schnitt).

**Empf. fürs Gate:** F1a + F2-Upgrade + F3(a) sind zusammen golden-neutral und erfüllen die Doktrin, ohne die Ebene-1-Enum zu brechen. F1b nur bei ausdrücklichem Ebene-1-Promotions-GO.
