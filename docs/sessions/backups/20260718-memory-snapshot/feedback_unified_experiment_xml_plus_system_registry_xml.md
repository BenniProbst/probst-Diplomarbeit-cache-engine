**User-Direktive 2026-07-13 (Klarstellung zur XML-Experiment-Architektur):**

Drei XML-Artefakte, klar getrennt:
- **ZWEI Registry-XMLs, GLEICHES Schema (System-Ebene):** (1) **ce-Registry** katalogisiert die je Achse in der CACHE-ENGINE vorhandenen Bausteine (Stand der Technik); (2) **prt-art-Registry** katalogisiert die je Achse im PRT-ART vorhandenen Bausteine — abstrakt, auf Basis der ce-C++23-Bibliothek. **Die Bausteine je Achse stehen NUR in den Registries (je Engine, nach dort vorhandenen Achsen-Algorithmen), NICHT in der Diplomarbeit-XML.** (permutation_axes.xml koennte die ce-Registry SEIN → dann TABU-read-only + prt-art-Registry additiv daneben — im Design-Workflow zu klaeren.)
- **Diplomarbeit-Experiment-XML = individuelle Config**: definiert NUR die Experimentier-VORLAGE — die **3 Phasen der Pruefung** (Phase 1 prt-art / Phase 2 cache-engine / Phase 3 kombinierte Achsen von beiden = 3-Stufen-Join `pruefling_merge.hpp` Stufe1/2/3) + welche Engines/Lebewesen + Mess-Settings (3 Mess-Modi, workloads, datasets, measurement_categories, op_types, output). Sie **referenziert die zwei Registries, listet SELBST keine per-Achse-Bausteine**; sie weist die Cache-Engine an, den prt-art mit dessen abstrakter Registry-Definition durchzumessen. Vereint die heutige Familie A (`comdare_thesis_profile`) + Familie C (`messreihe_v32`)-Experiment-Aspekte in EINEM Dokument.
- **v32-Modul → STRATEGY-PATTERN** der Experimentier-Configs (professionelle Architektur; jede Phase/Config = eine Strategy).

**Harte Zusatz-Constraints (User 13.07.):**
- **Pruefling-Registries befolgen das ce-Parser-Schema HART** (strikt gleiches Schema) — nur so ist der Pruefling gegen den Stand der Technik (ce) testbar. Keine Schema-Abweichung erlaubt.
- **Anwender-Rolle:** die Diplomarbeit ist der Anwender, der das Experiment (Ablauf+Aussehen) klar festlegt; die Cache-Engine ist die ausfuehrende Engine.
- **E2E-Kette ce-getrieben:** die Cache-Engine kompiliert das Experiment EXAKT wie in der Experiment-XML vorgesehen, baut die Tier-Binaries auf (sota_catalog→COMDARE_DEFINE_ANATOMY_MODULE→DLL) und fuehrt die im Plan inbegriffenen Experimente durch.
- **FOLGE-PFLICHT nach der Prinzip-Erweiterung:** ALLE Plaene/Doks, die auf dem E2E-Prinzip aufbauen (E1-E4-Maschinerie, xml→pdf-Kette, architektur/*, Dossiers), erneut gegen ALLE Anforderungen pruefen UND erweitern. Eigener Audit-Durchlauf (ultracode) NACH der Implementierung der erweiterten Architektur.
- **CacheEngineBuilder (CEB) = die EINE zentrale C++-Anwendung (User 13.07.):** ALLE XML-Parser (Registries + Experiment) sind IN der CEB-Anwendung verankert; sie steuert nach Anwender-Aufruf das gesamte Experiment. Die Tier-Binaries werden ZUR LAUFZEIT vom CEB gebaut (C++-orchestrierter Compiler-Aufruf je Permutation); der CEB HAELT auch das PRUEFDOCK und das MESSSYSTEM.
- **ZENTRALISIERUNG (User 13.07., spaeteres TODO):** der CacheEngineBuilder wird DAS zentrale EXPERIMENT-FRAMEWORK. Alle Tools der 4 Repos KARTIEREN; die FRAMEWORK-Tools (super/ce) STRATEGISCH in den CEB mergen: Registry-Generator, 0X-Pipeline-Stufen (03/04/05/08), latex_anhang, messung_driver, v32-Parser. Der CEB kann zusaetzlich die DIPLOMARBEIT-CODE-GENERATOREN als BIBLIOTHEK aufnehmen (Excel- + PDF-Auswertungen). Ziel = EIN zentrales System nach dem XML-Aufbau, KEIN verteiltes. **⚠️ prt-art bleibt ein SEPARATER PRUEFLING (NICHT in den CEB gemergt)** — liefert nur seine abstrakte Registry (gleiches Schema), wird gegen den SOTA getestet ([[feedback_prt_art_consumes_cache_engine]]). Gated nach INC-A..H; Tools nie loeschen — deprecaten+konsolidieren.
- **Nur EINE Steuerung in C++, moeglichst NICHT CMake (Performance, User 13.07.):** die Experiment-/Tier-Binary-Orchestrierung ist C++-getrieben (der CEB, nicht CMake-Logik/Re-Configure je Permutation — bei 320+ Binaries sonst katastrophal langsam). CMake baut NUR die ce-Lib + die CEB-Executable einmalig. Konkret: der Registry-Generator ist ein C++-Tool (vom CEB/C++ gesteuert), KEIN CMake-`COMDARE_GEN_AXIS_REGISTRY`-Option. (Gilt neben [[feedback_no_python_in_buildchain]]/[[feedback_immer_schwerer_offizieller_weg_keine_behelfswege]]: CMake bleibt der offizielle LIB-Build; die EXPERIMENT-Steuerung ist C++.) Die Experiment-Ausfuehrung (F/G-Verdrahtung) laeuft DURCH den CEB (baut Tier-Binary aus compile-time-Komposition → treibt sie durch das Pruefdock → misst ueber das Messsystem), NICHT ueber direkt konstruierte Engine-Adapter. Der Welch/EE-A-EE-B-Verdikt-Layer konsumiert die Messungen aus dem CEB-Messsystem via Pruefdock (PruefDockRegistry::select_for by genus, mess-transparent CE-Tier UND Pruefling-Tier). Ersetzt die quarantaenisierten Surrogat-Adapter (PrtArtHashBackend=std::unordered_map).

- **Parser = MODUL im allgemeinen Cache-Engine-Parser**: der Parser fuer das Experiment-XML gehoert als Modul in den allgemeinen Parser, den die Diplomarbeit nutzt (`ce/libs/common/serialization/xml_config_parser`, `parse_thesis_profile`), NICHT standalone. Der 13.07. gebaute standalone `super/Code/02_messung_driver/messreihe_v32_parser.hpp` (super 6a40fb9) ist eine Zwischenstufe → integriert als ce-Modul; der super-Standalone wird deprecatet (nicht geloescht). WAS/WIE: Framework-Parser = ce.

**Why:** Die xml→pdf-Kette + der Pruefling-Vergleich (Familie C = SOTA-Achse vs Pruefling-Achsen-Algorithmen ueber die 3 Mess-Kombinationen, [[feedback_axes_optimization_semantics_deep_research_observer_strategy]]) sollen aus EINEM deklarativen Experiment-Dokument gesteuert werden (#229 „nur die XML aendern"). Zwei getrennte Schema-Familien (A vs C) waren der Ist-Zustand, nicht das Ziel. Der Pruefling (PRT-ART) wird NIE hart verdrahtet, sondern compile-time per Config/Registry-XML in genau eine Achse substituiert (PrueflingSlot/3-Stufen-Join, [[reference_meta_driven_concept_hardening_pattern]]); das „NIE verdrahten"-Banner ist KORREKT (verbietet nur den Surrogat-Adapter, nicht den Vergleich).
