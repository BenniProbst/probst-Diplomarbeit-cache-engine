## 1. clang-format / clang-tidy als harte Gates

- **clang-format-Hard-Gate (kanonisch):** `clang-format --dry-run --Werror <files>` — `--dry-run` ändert nichts, `--Werror` macht Format-Abweichungen zu Fehlern → Exit ≠ 0 bricht den Job. Mit `--style=file` gegen die versionierte `.clang-format`; `--fallback-style=none` verhindert stilles Ausweichen auf LLVM-Defaults. Quelle: https://clang.llvm.org/docs/ClangFormat.html
- **Versions-Pinning ist Pflicht:** Format-Output ändert sich zwischen clang-format-Major-Versionen auch bei identischer Config; unbekannte (neuere) Optionen in der Config führen je nach Version zu abweichendem Format oder Fehlern ("might lead to dramatically differing format depending on an option being supported or not"). Praxis: exakte Version pinnen, z. B. via PyPI-Wheel `pip install clang-format==19.1.x` (ssciwr-Wheels, "stable output, as long as the same version is used") oder festes apt.llvm.org-Paket; Version im Repo dokumentieren (bei COMDARE: in `scripts/prod-runner-toolchain-setup.sh` fixieren). Quellen: https://pypi.org/project/clang-format/ · https://github.com/ssciwr/clang-format-wheel
- **Diff-only-Format-Gate für MRs:** `git clang-format --diff origin/main --extensions cpp,hpp,h` prüft nur den MR-Diff. Achtung Altbug: im `--diff`-Modus war der Return-Code ≠ 0 selbst OHNE Änderungen (gefixt via git-diff `--exit-code`, LLVM-Review D129311) → LLVM ≥ 15/16 verwenden oder Output statt Exitcode prüfen. Quellen: https://reviews.llvm.org/D129311 · https://github.com/llvm/llvm-project/issues/56736
- **clang-tidy hart schalten:** `--warnings-as-errors='*'` bzw. in `.clang-tidy` `WarningsAsErrors: '*'` — "Upgrades warnings emitted under the -checks= flag to errors (but it does not enable any checks itself)" → Exit ≠ 0. Checks-Liste ist davon getrennt zu pflegen. Quelle: https://clang.llvm.org/extra/clang-tidy/
- **Bestandscode-Strategie A (kuratierte Liste, repo-weit hart):** klein starten (`Checks: 'bugprone-*,clang-analyzer-*,performance-*'`, gezielte Abschaltungen), Liste inkrementell erweitern, sobald der Bestand sauber ist. Empfohlenes Muster in der Community-Praxis: "Enable on a curated check set in CI, gate on violation delta rather than zero." Quelle: https://sqglobe.com/2026/04/17/why-clang-tidy-matters-in-real-c-projects-and-how-to-set-it-up/
- **Bestandscode-Strategie B (diff-only):** `git diff -U0 origin/main...HEAD | clang-tidy-diff.py -p1 -path build -j$(nproc)` — meldet nur Diagnosen auf geänderten Zeilen; analysiert intern trotzdem die ganze Datei (kein Laufzeitgewinn) und verpasst Folgefehler außerhalb des Diffs. Quelle: https://github.com/llvm/llvm-project/blob/main/clang-tools-extra/clang-tidy/tool/clang-tidy-diff.py
- **Bestandscode-Strategie C (Baseline/Delta, sauberster Weg):** CodeChecker: Baseline einfrieren, Gate nur auf NEUE Reports: `CodeChecker cmd diff -b ./reports.baseline -n ./reports --new` (JSON-Output für Automation; Reports mit Status "False Positive"/"Intentional" fallen raus). Verhindert, dass Alt-Schuld blockiert, erzwingt aber Null-Neuzugang. Quelle: https://codechecker.readthedocs.io/en/latest/usage/
- **Vollanalyse parallelisieren:** `run-clang-tidy -p build -j N` gegen `compile_commands.json` (CMake: `CMAKE_EXPORT_COMPILE_COMMANDS=ON`); alternativ dauerhaft im Build via `CMAKE_CXX_CLANG_TIDY`. Quelle: https://clang.llvm.org/extra/clang-tidy/
- **HeaderFilter setzen** (`HeaderFilterRegex`), sonst Diagnosen aus ext/-Headern (Boost.MP11 etc.) im Gate; system headers bleiben default draußen. Quelle: https://clang.llvm.org/extra/clang-tidy/
- **Auditierbare Ausnahmen statt Gate-Aufweichung:** `// NOLINT(check)`, `// NOLINTNEXTLINE(check)`, `// NOLINTBEGIN(check) … // NOLINTEND` — immer MIT Check-Name, damit greppbar. Quelle: https://clang.llvm.org/extra/clang-tidy/
- **clang-tidy ebenfalls pinnen:** Checks/Diagnosen ändern sich pro Release (neue Checks können bestehende Pipelines brechen); gleiche Pinning-Quelle wie clang-format (PyPI-Wheel `clang-tidy==…` bzw. LLVM-Apt-Repo mit fixer Major).

## 2. Sanitizer-Stufen (ASan/UBSan/TSan/MSan)

- **Basissatz Debug-CI (Stufe 1, matrix-weit auf Unit-/Funktionstests):** `-fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer -g -O1` (+ `-fno-optimize-sibling-calls` für saubere Stacks). ASan+UBSan sind kombinierbar und der akzeptierte CI-Standard. Quellen: https://github.com/google/sanitizers/wiki/AddressSanitizer · https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html
- **Warum `-fno-sanitize-recover=all` das eigentliche HART-Schalten ist:** UBSan "prints a verbose error report and continues execution upon a failed check" — ohne Recover-Abschaltung endet der Prozess mit Exit 0 und das Gate ist wirkungslos. Gilt für clang UND GCC: GCC-Doku: "For these sanitizers error recovery is turned on by default" (undefined, float-cast-overflow, float-divide-by-zero, bounds-strict, kernel-address). Quellen: https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html · https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html
- **Runtime-Optionen im CI-Job:** `ASAN_OPTIONS=detect_leaks=1:detect_odr_violation=2:strict_string_checks=1`, `UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1`. Runtime-Defaults: `halt_on_error=1` bei ASan, `0` bei TSan/UBSan → für TSan/UBSan explizit setzen (bzw. Compile-seitig via `-fno-sanitize-recover`). LSan ist unter Linux bei ASan automatisch aktiv. Quellen: https://github.com/google/sanitizers/wiki/AddressSanitizer · https://www.jetbrains.com/help/clion/google-sanitizers.html
- **Optimierungsstufe:** `-O1` ist der Sweet-Spot (Doku-Empfehlung); `-O0` = langsam, `-O2/-O3` kann UB wegoptimieren, bevor UBSan es sieht → Sanitizer-Jobs nicht auf dem Release-Profil fahren. Quelle: https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html
- **TSan = gezielt, NICHT matrix-weit:** Slowdown ~5x–15x, Speicher ~5x–10x (+1 MB/Thread) → eigener Job nur für die Concurrency-Testsuite. Flags: `-fsanitize=thread -O1 -g`; `TSAN_OPTIONS="halt_on_error=1 second_deadlock_stack=1"`; Suppressions via `TSAN_OPTIONS=suppressions=tsan.supp`. Nicht mit ASan kombinierbar (GCC-Doku: "cannot be combined with -fsanitize=address"). Quellen: https://clang.llvm.org/docs/ThreadSanitizer.html · https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html
- **MSan = clang-only und teuer im Setup:** GCC hat KEIN `-fsanitize=memory`; MSan verlangt, dass ALLE Abhängigkeiten inkl. Standard-C++-Bibliothek instrumentiert sind (eigener libc++-Build), sonst False Positives; Slowdown ~3x, RAM 2x–3x. Für einen g++-Runner-Stack: weglassen oder späteres clang-Nebenprofil mit instrumentiertem libc++. Quellen: https://clang.llvm.org/docs/MemorySanitizer.html · https://github.com/google/sanitizers/wiki/MemorySanitizerLibcxxHowTo · https://developers.redhat.com/blog/2021/05/05/memory-error-checking-in-c-and-c-comparing-sanitizers-and-valgrind
- **g++ vs clang++ (relevant für COMDARE-Matrix):** GCC bietet address/hwaddress/thread/leak/undefined (+`bounds-strict`, `pointer-compare`, `pointer-subtract`); clang-exklusiv sind u. a. `implicit-conversion`, `integer`, `nullability-*`, `local-bounds`, `function` sowie memory/dataflow/cfi. Ein clang-Zweitjob findet also zusätzliche Fehlerklassen. Quellen: https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html · https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html
- **ASan-Extras (beide Compiler):** `-fsanitize=pointer-compare,pointer-subtract` + `ASAN_OPTIONS=detect_invalid_pointer_pairs=2` (Runtime-Check ist per Default AUS). Quelle: https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html
- **Billige Nicht-Sanitizer-Härtung im Debug-CI:** `-D_GLIBCXX_ASSERTIONS` (libstdc++-Precondition-Asserts, ABI-stabil) matrix-weit; `-D_GLIBCXX_DEBUG` (ABI-BRECHEND) nur als isolierter Extra-Job. Quelle: https://gcc.gnu.org/onlinedocs/libstdc++/manual/using_macros.html
- **Absolutes Tabu:** Sanitizer-Flags niemals in Mess-/Benchmark-Builds — sie verfälschen Laufzeit UND Allokationsverhalten komplett; Mess-Profil strikt getrennt halten.
- **Matrix-Empfehlung:** Job A = g++ ASan+UBSan (alle Tests, hart) · Job B = clang++ ASan+UBSan (Zweitmeinung, hart nach Stabilisierung) · Job C = TSan nur Concurrency-Suite (hart) · MSan = deferred/optional.

## 3. Benchmark-/Mess-Validitäts-Gates

- **Grundsatzbefund 2025/26:** Perf-Vergleiche ÜBER CI-Läufe hinweg sind nur auf ruhiggestellten bare-metal-Runnern belastbar; auf shared/virtualisierten Runnern gilt "run benchmarks on main, then on your feature branch, and compare" im selben Job als einzig sinnvolles Muster. HART schaltbar sind primär VALIDITÄTS-Gates; Perf-Delta-Gates erst mit Statistik + Historie. Quellen: https://dev.to/kienmarkdo/low-noise-ec2-benchmarking-a-practical-guide-19f0 · https://buttondown.com/nelhage/archive/f6e8eddc-b96c-4e66-a648-006f9ebb6678
- **Hartes Smoke-Gate (sofort, pro MR):** `--benchmark_dry_run` — "run the benchmarks as normal, but for 1 iteration and 1 repetition only" (google/benchmark ≥ v1.9). Beweist Lauffähigkeit ALLER Prüflinge ohne Messkosten. Quelle: https://github.com/google/benchmark/blob/main/docs/user_guide.md
- **Hartes Umgebungs-Validitäts-Gate:** google/benchmark schreibt in den JSON-Output-Context u. a. `cpu_scaling_enabled`; CI-Skript prüft vor dem Messlauf Governor=performance, Turbo aus, erwartete CPU — sonst FAIL (lieber Messung verwerfen als falsche Daten produzieren). Quelle: https://github.com/google/benchmark/blob/main/docs/reducing_variance.md
- **compare.py korrekt einsetzen:** Mann-Whitney-U-Test (Nullhypothese: kein Unterschied), `--alpha` Default 0.05, U-Test "requires LARGE (no less than 9) number of repetitions to be meaningful!". ABER: compare.py exitet NICHT nonzero bei Regression (nur bei Input-Fehlern, verifiziert im Quellcode) → als hartes Gate eigenen Wrapper um `--dump_to_json`-Ergebnis bauen, der bei p < alpha UND Delta > Schwelle failt. Quellen: https://github.com/google/benchmark/blob/main/docs/tools.md · https://github.com/google/benchmark/blob/main/tools/compare.py
- **Einziges robustes hartes Perf-Muster = Same-Run-A/B:** Baseline-Binary (main) und Contender im SELBEN Job auf DERSELBEN Maschine bauen und interleaved messen: `--benchmark_enable_random_interleaving=true --benchmark_repetitions=9` ("lower run-to-run variance by 40% on average"); ggf. `--benchmark_min_time=0.1` je Repetition. Quelle: https://github.com/google/benchmark/blob/main/docs/random_interleaving.md
- **Quiescing bare-metal (LLVM-Rezept, Ziel "perf variations of less than 0.1%"):** `cset shield -c N1,N2 -k on` (Kern-Isolation inkl. Kernel-Threads) · ASLR aus: `echo 0 > /proc/sys/kernel/randomize_va_space` · Governor: `echo performance > /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor` · Turbo aus: `echo 1 > /sys/devices/system/cpu/intel_pstate/no_turbo` (AMD: `…/cpufreq/boost` = 0) · SMT-Siblings offline (`/sys/devices/system/cpu/cpuX/online`, Siblings via `topology/thread_siblings_list`) · Lauf: `cset shield --exec -- perf stat -r 10 <cmd>`. Quelle: https://llvm.org/docs/Benchmarking.html
- **Alternativ Kernel-cmdline (statisch statt cset):** `isolcpus=<liste> rcu_nocbs=<liste> nohz_full=<liste>`; Komplett-Checkliste inkl. IRQ-Affinity: pyperf-System-Doku (`python -m pyperf system tune` automatisiert Governor/Turbo/ASLR/IRQ). Quellen: https://pyperf.readthedocs.io/en/latest/system.html · https://github.com/google/benchmark/blob/main/docs/reducing_variance.md
- **Wiederholungen/Statistik als hartes QUALITÄTS-Gate:** `--benchmark_repetitions=N` (N ≥ 9) + `--benchmark_report_aggregates_only` liefert mean/median/stddev/cv; Gate auf `cv < X %` (z. B. 2–5 %) pro Benchmark hart schalten = "Messung zu verrauscht → Lauf ungültig, wiederholen" statt falscher Vergleich. Median/robuste Statistik gegenüber Mean bevorzugen; Winsorisierung/Trimmen nur dokumentiert (Wissenschaftlichkeit!).
- **Kontinuierliche Verfahren mit Historie:** Bencher (self-hostable) legt Thresholds pro Branch/Testbed/Measure an; statistische Tests: `static`, `percentage`, `z_score`, `t_test`, `log_normal`, `iqr`, `delta_iqr` mit Upper/Lower-Boundary → Alert/Gate; braucht historische Baseline des Zielbranches. Quellen: https://bencher.dev/docs/explanation/thresholds/ · https://bencher.dev/docs/how-to/gitlab-ci-cd/
- **Change-Point-Detection (Stand der Technik für Messreihen):** Apache Otava (ex-Hunter, MongoDB/DataStax/Confluent-Praxis): E-Divisive-Familie + t-Test statt randomisierter Permutation (deterministisch), Sliding-Window; arbeitet auf CSV/PostgreSQL/BigQuery/Graphite-Zeitreihen. CPD ist inhärent ASYNC/advisory (erkennt Regressionen über die Serie, nicht zuverlässig pro einzelnem MR). Quellen: https://otava.apache.org/docs/math/ · https://github.com/apache/otava · https://ar5iv.labs.arxiv.org/html/2301.03034
- **GitLab-native Anzeige (advisory):** `artifacts:reports:metrics` (OpenMetrics-Textformat) → MR-Widget zeigt geänderte/neue/entfernte Metriken vs. Target-Branch; NUR Premium/Ultimate. Auf CE: compare.py-Report als Artefakt + MR-Kommentar via API. Quelle: https://docs.gitlab.com/ci/testing/metrics_reports/
- **Gate-Aufteilung (Merksatz):** HART = dry_run + Umgebungs-Check + Repetitions/CV + Output-Vollständigkeit (alle erwarteten Benchmarks im JSON). ADVISORY = Perf-Delta pro MR (Report). HART-Perf erst nach stabiler Historie, dann Same-Run-A/B + U-Test/IQR mit relativer Schwelle — nie roher Einzelwert-Vergleich.
- **Mehrtages-Messläufe:** nie als MR-Gate; eigener scheduled/manual Pipeline-Typ; Roh-Ergebnisse persistieren (MESSDATEN NIE LÖSCHEN) und asynchron per Otava/Bencher auswerten.

## 4. LaTeX-Thesis-Gates (chktex/latexmk)

- **Build-Gate hart (sofort):** `latexmk -pdf -file-line-error -interaction=nonstopmode -halt-on-error main.tex` → Exit ≠ 0 bei Compile-Fehler; latexmk orchestriert alle nötigen Läufe (biber/bibtex/Index) selbst. `-interaction=nonstopmode` verhindert Hängen auf User-Input im CI. Quelle: https://www.mankier.com/1/latexmk
- **Referenz-/Zitations-Gate hart:** `latexmk -Werror …` — wörtlich: "return a non-zero status code if any of the files processed gives a warning about problems with citations or references (i.e., undefined citations or references or about multiply defined references) … only when they occur on the last run". Für eine Diplomarbeit das wertvollste LaTeX-Gate überhaupt (fängt kaputte \ref/\cite nach allen Läufen). Quelle: https://www.mankier.com/1/latexmk
- **`-f` (force) NICHT im Gate-Job verwenden** — es erzwingt Weiterverarbeitung trotz Fehlern und maskiert den Exitcode-Sinn. Quelle: https://www.mankier.com/1/latexmk
- **chktex-Exitcode-Falle:** chktex liefert Exit 0 auch bei Warnungen → hartes Gate nur via Output-Prüfung: `chktex -q -n8 -n22 … main.tex 2>/dev/null | tee chktex.out; test ! -s chktex.out` (etabliertes GitLab-CI-Muster). Quellen: https://blog.martisak.se/2020/05/11/gitlab-ci-latex-pipeline/ · https://manpages.debian.org/bookworm/chktex/chktex.1.en.html
- **Fehlklassen-Steuerung:** `-n<num>`/`--nowarn` mutet Warnung Nr. num, `-w`/`-e` stufen zu Warnung/Fehler um; projektweite Kalibrierung in versionierter `.chktexrc` (via `-l/--localrc` bzw. Projektroot). Typisch gemutet werden Interpunktions-/Spacing-Heuristiken, die bei deutschem Text und eigenen Makros false-positive sind — Mute-Liste einmalig im Format-Pass kalibrieren, danach einfrieren. Quelle: https://manpages.debian.org/bookworm/chktex/chktex.1.en.html
- **Stufung:** latexmk-Build + `-Werror` SOFORT hart; chktex zunächst advisory (Report-Artefakt), nach Kalibrierung der Mute-Liste hart (test ! -s Muster).
- **texlive-Docker vs. nativ:** Island-of-TeX-Images (`registry.gitlab.com/islandoftex/images/texlive:TL2025-…`) sind der Reproduzierbarkeits-Standard: Jahres-Tags, historische Releases ab 2014, monatliche Rebuilds, seit 02/2025 non-root `texlive`-User; Flavors minimal/doc/src. Für eine Thesis (Reproduzierbarkeit = wissenschaftlicher Anspruch) Docker-Image mit Jahres-Tag pinnen. Quellen: https://gitlab.com/islandoftex/images/texlive · https://islandoftex.gitlab.io/community/projects/docker/
- **Bare-metal-Abwägung:** Full-Image ist mehrere GB — auf dediziertem Runner einmalig gepullt/gecacht ⇒ Einmalkosten; native TeXLive-Installation nur, wenn Docker auf dem Runner nicht verfügbar ist, dann TL-Jahresstand einfrieren + in Toolchain-Doku festhalten (sonst schleichende Paket-Drift).
- **Overleaf-Drift vermeiden (COMDARE-Topologie: Overleaf pusht auf GitHub-origin):** TL-Version des CI-Images an die von Overleaf verwendete TeX-Live-Version angleichen, sonst "baut nur in CI / nur in Overleaf"-Divergenzen.

## 5. Coverage-/Doku-Gates

- **gcovr harte Schwellen mit definierten Exitcodes:** `--fail-under-line MIN` (Exit 2) · `--fail-under-branch MIN` (Exit 4) · `--fail-under-decision MIN` (Exit 8) · `--fail-under-function MIN` (Exit 16); Codes kombinieren sich bitweise. Quelle: https://gcovr.com/en/stable/manpage.html
- **GitLab-Integration:** `gcovr --cobertura coverage.xml --cobertura-pretty --print-summary` + im Job `artifacts:reports:coverage_report: {coverage_format: cobertura, path: coverage.xml}` → Zeilen-Annotation im MR-Diff; Anzeige-Prozentwert via `coverage: '/^\s*lines:\s*\d+.\d+\%/'`. Quellen: https://docs.gitlab.com/ci/testing/code_coverage/cobertura/ · https://gcovr.com/en/stable/manpage.html
- **C++-Branch-Rauschen filtern:** `--exclude-unreachable-branches` (compilergenerierter Dead-Code) und `--exclude-throw-branches` (Exception-Handling-Branches) — ohne beides sind C++-Branch-Quoten strukturell sinnlos niedrig. Quelle: https://gcovr.com/en/stable/manpage.html
- **Instrumentierung strikt trennen:** eigener Coverage-Build `g++ --coverage -O0 -g` (= `-fprofile-arcs -ftest-coverage`); NIE im Mess-Profil. lcov-2.x-Alternative hat `--fail-under-lines`, gcovr ist für GitLab-Cobertura der direktere Weg.
- **Lohnt Coverage für ein Mess-Framework?** Ja — aber NUR auf dem korrektheitskritischen Kern (Achsen-Registry, Adapter/Fassaden, Statistik-/Auswertelogik, Verifikationsstufen), eingeschränkt via `gcovr --filter`/`-f` auf Kern-Verzeichnisse; Benchmark-Bodies/Prüflinge und generierter Permutationscode verzerren die Quote und gehören ausgeschlossen (`-e`). Kern-Schwelle realistisch (z. B. line ≥ 80) hart, Gesamtquote nur advisory.
- **Doxygen hart:** `WARN_AS_ERROR = FAIL_ON_WARNINGS` — sammelt ALLE Warnungen und exitet am Ende ≠ 0 (besser als `YES`, das beim ERSTEN Warning sofort stoppt); `FAIL_ON_WARNINGS_PRINT` schreibt Warnungen gebündelt ans Ende; `WARN_LOGFILE` als CI-Artefakt. Warnungsmenge über `WARN_IF_UNDOCUMENTED`/`WARN_IF_INCOMPLETE_DOC` steuern. Quellen: https://www.doxygen.nl/manual/config.html · https://github.com/doxygen/doxygen/issues/8747
- **Praxis-Reihenfolge (NOAA/libcamera-Muster):** erst Doxygen-Warnungen abbauen, DANN `WARN_AS_ERROR` einschalten, "to cause the CI build to break if someone commits code without proper doxygen documentation". Quellen: https://github.com/NOAA-EMC/UPP/issues/392 · https://patchwork.libcamera.org/patch/20044/
- **Priorisierung fürs Mess-Framework:** Doxygen-Gate = mittlere Priorität (öffentliche Achsen-/Adapter-API dokumentationspflichtig, interner Messcode nicht); Coverage-Gate = sinnvoll ab stabiler Kern-API, vorher nur Anzeige.

## 6. GitLab-spezifisch (allow_failure, needs, interruptible/auto_cancel, resource_group)

- **allow_failure-Defaults:** `false` regulär; `true` bei `when: manual`; ABER `false` bei `when: manual` INNERHALB von `rules`. Job mit allow_failure=true zeigt orangenes "!" — Pipeline bleibt bestehbar. Quelle: https://docs.gitlab.com/ci/yaml/
- **Migrationsstrategie advisory → hart:** (1) Gate-Job mit `allow_failure: true` einführen (Sichtbarkeit ohne Blockade), (2) Befund-Backlog abbauen (Format-/Fix-Pass), (3) im selben Commit wie der letzte Fix `allow_failure` entfernen. Feingranular: `allow_failure: exit_codes: [42]` — Prüfskript liefert z. B. Exit 42 = "nur Alt-Befunde" (toleriert) vs. Exit 1 = "neue Befunde" (hart) → sauberer Delta-Gate-Mechanismus auf GitLab-Ebene. Quelle: https://docs.gitlab.com/ci/yaml/
- **needs-Ketten:** DAG löst Jobs von Stage-Reihenfolge; Limit default 50 `needs` pro Job (self-managed via Plan-Limits-API `ci_needs_size_limit` änderbar; 0 = needs verboten); `needs: []` startet Job sofort — ideal, damit Lint-/Format-Gates parallel zum Compile laufen statt danach. Quellen: https://docs.gitlab.com/administration/cicd/limits/ · https://docs.gitlab.com/ci/yaml/
- **interruptible/auto_cancel-Semantik:** `interruptible` default `false`. `workflow:auto_cancel:on_new_commit`: `conservative` (Default) = "Cancel the pipeline, but only if no jobs with interruptible: false have started yet" · `interruptible` = "Cancel only jobs with interruptible: true" · `none` = nichts canceln. Seit GitLab 16.10 ist `interruptible` in `rules:` schaltbar (z. B. `interruptible: false` nur auf protected refs via `CI_COMMIT_REF_PROTECTED`). Quellen: https://docs.gitlab.com/ci/yaml/ · https://support.gitlab.com/hc/en-us/articles/22118112967068-How-to-auto-cancel-redundant-pipelines
- **Mehrtages-Messjobs schützen (KRITISCH für COMDARE):** Mess-Jobs explizit `interruptible: false`; Pipeline-Typ der Messläufe mit `workflow:auto_cancel:on_new_commit: none`; Projekt-Setting "Auto-cancel redundant pipelines" mitdenken. `on_job_failure: all` NIEMALS in Mess-Pipelines setzen ("Cancel the pipeline and all running jobs as soon as one job fails" würde den Messlauf killen, wenn ein Nebenjob failt) → `none` (Default) belassen. Quelle: https://docs.gitlab.com/ci/yaml/
- **Timeout-Hierarchie für lange Jobs:** Projekt-Timeout default 60 min, Maximum "less than one month"; Job-Keyword `timeout:` pro Job; Runner-`maximum_timeout` gewinnt, wenn KLEINER ("The maximum job timeout is used if it is shorter than the job timeout defined in the project"; Runner 24h + Projekt 2h → 2h; Runner 30min + Projekt 2h → 30min) → für den Mess-Runner `maximum_timeout` groß/leer lassen UND Job-`timeout: 7d` o. ä. setzen. Quellen: https://docs.gitlab.com/ci/pipelines/settings/ · https://docs.gitlab.com/ci/runners/configure_runners/
- **Output-Stille-Falle:** GitLab-Settings-Doku: "Jobs without an output for one hour are dropped regardless of the timeout" → stille Mess-Phasen brauchen Heartbeat-Logging (deckt sich mit der #210-Watchdog-Erfahrung); Verhalten auf der eigenen Instanz-Version verifizieren. Quelle: https://docs.gitlab.com/ci/pipelines/settings/
- **resource_group für Exklusiv-Messungen:** `resource_group: perf-rig` serialisiert alle Jobs dieser Gruppe projektweit ÜBER Pipelines hinweg (ein Job zur Zeit auf dem Mess-Rig). `process_mode` default `unordered`; Alternativen `oldest_first` (FIFO nach Pipeline-ID), `newest_first`, `newest_ready_first` — Umschalten NUR per API: `PUT /projects/:id/resource_groups/:key` mit `process_mode`. Quelle: https://docs.gitlab.com/ci/resource_groups/
- **resource_group-Deadlock-Falle:** `oldest_first` + Parent-/Child-Pipeline, die DIESELBE resource_group brauchen → Deadlock; Lösung laut Doku: resource_group im Parent (Trigger-Job) definieren statt im Child. Quelle: https://docs.gitlab.com/ci/resource_groups/
- **resource_group ersetzt keine Runner-Exklusivität:** zusätzlich dedizierter Runner-Tag + Runner-`limit`/`concurrent`-Beschränkung; resource_group verhindert nur Konkurrenz INNERHALB der Gruppe/des Projekts — beides kombinieren (deckt sich mit COMDARE-Direktive "Runner halbe Host-Kerne, concurrent=2" → Mess-Runner separat mit concurrent=1).
- **Metrics-Widget** (`artifacts:reports:metrics`, OpenMetrics, Delta im MR) = Premium/Ultimate — auf CE stattdessen Report-Artefakt + MR-Note per API. Quelle: https://docs.gitlab.com/ci/testing/metrics_reports/
