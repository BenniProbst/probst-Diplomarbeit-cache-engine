  SYN ← "Trie Node"                    P09 Jacobson1989 (succinct)

      des Schluessels und gibt Folgepointer/Folgeposition zurueck.
  BEL P01 ART: "Inner nodes of size 4, 16, 48, 256 (...) all four data structures

  ABG NICHT "Page" (eine Page kann mehrere Knoten enthalten)
      NICHT "Cache Line" (Hardware-Granularitaet)

1.5  SUCCINCT/SPACE-EFFICIENT FAMILIE (mit Jacobson + SuRF integriert)

[KANON]  SUCCINCT TREE-ENCODING
  SYN ← "Succinct Tree"              P09 Jacobson1989 (LOUDS, Originalpaper)
  SYN ← "Space-efficient Tree"       P09 Jacobson1989 (Titel)
  SYN ← "Compact Tree"               allgemein
  SYN ← "Implicit Encoding"          P09 Jacobson1989
  SYN ← "Fast Succinct Trie (FST)"   P10 SuRF (Sec.4)
  BED Tree-Repraesentation mit ~Information-theoretical Lower Bound bits/Knoten.
      ~2 bits/node fuer binaeren Baum (Jacobson), ~10 bits/key fuer SuRF FST.
  BEL P09 Jacobson: "any tree of n nodes can be encoded in 2n + o(n) bits
      while supporting parent, child, degree queries in O(1)" (P09:Sec.1)
      P10 SuRF: "FST (Fast Succinct Trie) achieves 10 bits per key on average"
      (P10:Sec.4)
  ABG NICHT "compressed" (allgemein); succinct = nahe theor. Lower Bound,
      compressed = nur kleiner als trivial.

[KANON]  LOUDS-ENCODING (Level-Ordered Unary Degree Sequence)
  SYN ← "LOUDS"                      P09 Jacobson1989 (Originalterm)
  SYN ← "Level-Order Bit-String"     P09 Jacobson1989
  SYN ← "Unary Degree Sequence"      P09 Jacobson1989
  BED Bit-Sequenz der Form 1*0 pro Knoten (degree-Bits + Terminator), Knoten
      in BFS-Reihenfolge. Ermoeglicht O(1)-Navigation via rank/select.
  BEL P09 Jacobson: "BFS traversal of the tree, output unary representation
      of each node's degree (...) parent, first-child, next-sibling all in
      O(1) using rank and select on bit string" (P09:Sec.4)
  BEZ PRT-ART **Dense-Byte-Page** (oberhalb von Cache-Engine-Wahl) — PRT-ART
      braucht aber UPDATE-FAEHIGKEIT (LOUDS ist statisch).

[KANON]  LOUDS-DENSE
  SYN ← "LOUDS-Dense"                P10 SuRF (Sec.4.1)
  SYN ← "D-Labels / D-HasChild / D-IsPrefixKey"  P10 SuRF (3 Bitmaps a 256)
  BED SuRF Top-Levels Encoding: 3 Bitmaps der Groesse 256 (eine pro 256er-
      Verzweigungs-Byte) + Byte-Sequence fuer Werte. Cache-friendly.
  BEL P10 SuRF: "LOUDS-Dense uses three bitmaps each of size 256: D-Labels
      indicates which bytes branch, D-HasChild marks branches with subtries,
      D-IsPrefixKey marks prefixes that are keys" (P10:Sec.4.1)
  BEZ **DIREKT mappbar auf PRT-ART Dense-Byte-Page!**

[KANON]  LOUDS-SPARSE
  SYN ← "LOUDS-Sparse"               P10 SuRF (Sec.4.2)
  SYN ← "S-Labels / S-HasChild / S-LOUDS"  P10 SuRF (byte-bit-bit pro Knoten)
  BED SuRF Bottom-Levels Encoding: 3 Byte-Sequenzen, eine pro Trie-Knoten.
      Space-efficient, aber teurer Lookup.
  BEL P10 SuRF: "LOUDS-Sparse encodes each node with three sequences:
      S-Labels stores one byte per child, S-HasChild bit per child indicating
      subtree, S-LOUDS bit per child indicating end of node" (P10:Sec.4.2)
  BEZ **DIREKT mappbar auf PRT-ART Sparse Patricia Page!**

[KANON]  LOUDS-DS (Hybrid)
  SYN ← "LOUDS-DS"                   P10 SuRF (Sec.4.3)
  SYN ← "Hybrid Encoding"            P10 SuRF
  SYN ← "Cutoff Level R"             P10 SuRF (default R=64)
  BED Kombination: Top-Levels in LOUDS-Dense (cache-friendly), Bottom-Levels
      in LOUDS-Sparse (space-efficient). Schwelle R tunable.
  BEL P10 SuRF: "LOUDS-DS combines LOUDS-Dense for the upper R levels and
      LOUDS-Sparse for the lower levels (...) we choose R such that the
      LOUDS-Dense portion fits in CPU cache" (P10:Sec.4.3)
  BEZ **HOECHST RELEVANT** — diese Hybrid-Logik ist KONZEPTIONELL AEQUIVALENT
      zu PRT-ART **Cache-Engine Page-Type-Selection Rules**!
      SuRF (P10) statisch (Schwelle einmal); PRT-ART dynamisch (Cache-Engine
      runtime). DAS ist eine unserer 4 Forschungsluecken (Konzeptmatrix Cluster A).

[KANON]  RANK / SELECT

4 IDENTIFIZIERTE PRT-ART-FORSCHUNGSLUECKEN (Konsolidiert aus Konzeptmatrix)

LUECKE 1: Cache-Engine als getrennte Meta-Ebene
   Beleg: Keine der 33 Quellen P01-P33 hat eine getrennte Cache-Engine-Ebene.
   Alle haben Cache-Awareness "built-in" in der Algorithmus-Implementierung.
   PRT-ART loest dies durch saubere Trennung Such-Domaene ↔ Cache-Engine-Domaene.

LUECKE 2: Online Re-Layouting wird explizit ausgeschlossen
   Beleg: P28 Kuehn: "while we detect hot paths, runtime re-layouting is
   explicitly out of scope" (P28:Sec.4).
   P18 Saikkonen macht Multi-Level Relocation, aber statisch geplant.
   PRT-ART macht Online Re-Layouting via Cache-Engine-Modus 3.

LUECKE 3: Gemeinsame Wahl Seitentyp+Layout+Inline+Prefetch+Allocator
   Beleg: P10 SuRF waehlt nur Encoding (Dense/Sparse), P20 Mueller waehlt nur
   Layout, P14 Samuel waehlt Konfiguration aus Tabelle, P23 Khan waehlt nur
   Prefetch-Distanz. Keine Quelle waehlt ALLE 5 gemeinsam.
   PRT-ART Cache-Engine waehlt alle 5 in einem koordinierten Schritt.

LUECKE 4: Plattform-bewusste online Adaption pro ISA-Pfad
   Beleg: P31/P32/P33 (TUD/Habich-Linie) zeigen Plattform-Variabilitaet,
   aber ohne online Adaption pro ISA-Pfad zur Laufzeit.
   PRT-ART Modus 3 + ISA-Dispatch = neue Kombination.

NICHT-MEHR-OFFENE PUNKTE (gegenueber v2)
================================================================================

* "ChainRef" — vertagt (Termin 2). Mapping zu CoCo-trie Macro-Node ist NICHT
   direkt — Macro-Node ist Subtrie-Kollabierung, ChainRef ist Value-Verkettung.

* "Border Node" (Masstree P03) — Layer-Grenze (Slice-Wechsel). PRT-ART nutzt
   keine 8-Byte-Slices, daher nur konzeptionell aequivalent.

* "Fingerprinting" (B-Trees Are Back P20) — vorberechneter Hash-Bit-Vector
   pro Schluessel. PRT-ART Termin 1: optional, nicht im Pflicht-Kern.

* "Heads / Hints" (B-Trees Are Back P20) — sortierte erste Bytes der
   Schluessel im Page-Header. NICHT identisch zu PRT-ART Probability Hints
   (statistische Telemetrie). Verschiedene Konzepte.

* "Concurrency Token" / "Version" (P08 ART OLC, P03 Masstree) vs RCU Grace
   Period (P29) — komplementaer: OLC fuer Lookups, RCU fuer Memory Reclamation
   nach Relocation. PRT-ART nutzt im Kern beide (T4 Designentscheidung).

* SuRF "FST" + "LOUDS-Dense / LOUDS-Sparse" — VOLL INTEGRIERT in 1.5.
   LOUDS-Dense ↔ PRT-ART Dense-Byte-Page, LOUDS-Sparse ↔ Sparse Patricia Page,
   LOUDS-DS Hybrid ↔ Cache-Engine Page-Type-Selection. SuRF statisch, PRT-ART
   dynamisch.

* "TUD/Habich-Linie" (P31/P32/P33) — Sprache + Methodik der Diplomarbeit-
   Forschungslinie. P31 Ungethuem 2017 ist die Sprache, P32 Schmidt 2025 die
   empirische Plattform-Stuetze, P33 VAMPIR die NFP-Sprache.

* "Saikkonen Multi-Level Relocation" (P18) + "Layout-Invariante" (P19) —
   direkter Vorgaenger fuer PRT-ART Online Relocation, aber statisch geplant.
   PRT-ART macht das adaptiv via Cache-Engine.

* "Hot Path Detection ohne Re-Layouting" (P28 Kuehn) — explizit als
   Forschungsluecke benannt: PRT-ART schliesst diese Luecke.

* "Useless Prefetch" (P24 NaderanTahan) — klassisches Argument fuer Adaptive
   Prefetch in PRT-ART Cache-Engine.

* "Fill Buffer als limitierender Faktor" (P25 Mahling) — Hardware-Begrenzung,
   die PRT-ART Cache-Engine bei Prefetch-Distanz-Wahl beruecksichtigt.
