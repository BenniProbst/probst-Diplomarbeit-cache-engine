KORREKTUR D-1 — §1(C) CACHEENGINE-LOKATION  (F12-K)
================================================================================

WAS v3 SAGT
   "(C) CACHE-ENGINE-LOKATION
       Die Cache Engine ist KEIN separates globales Singleton-Heap-Modul.
       Sie lebt IM `CacheEngineBuilder` (= main.cpp Orchestrator).
       Sie wird zwischen Modul-Experimenten zurueckgesetzt."

KORREKTUR v4
   "(C) CACHE-ENGINE-LOKATION  (KORRIGIERT)
       Die Cache Engine IST ein Heap-Singleton, lebt aber INNERHALB des
       CacheEngineBuilder-Prozesses als globale Variable. Sie ist KEIN
       separater Prozess und KEINE Member-Variable des Builders, sondern
       eine Singleton-Instanz im Builder-Prozess-Heap.
       Sie wird Such-Algorithmus-Modulen als RESSOURCE bereitgestellt
       (via `CacheEngine::instance()` oder injizierte Referenz beim
       Modul-Bind).
       Sie bietet einen Observer-Slot, ueber den Module ihre
       Entscheidungszustaende generieren.
       Cache-Warmup gehoert ZUR Algorithmus-Permutation; CacheEngine.reset()
       setzt internen Zustand zurueck (NICHT die Instanz)."

ARCHITEKTUR-DIAGRAMM (KORRIGIERT)
   CacheEngineBuilder = main.cpp Orchestrator (Prozess)
     │
     └─► Heap-Region des Prozesses
            │
            ├─► CacheEngine::instance()             [Singleton, global]
            │     • ConcurrencyManager::instance()  [Sub-Singleton]
            │     • DecisionLambdaTrees aus geladenem Modul
            │     • InMemoryMeasurementBuffer
            │     • ObserverRegistry
            │
            └─► Dynamisch geladene Module           [pro Experiment]
                  └─► binden CacheEngine::instance() als Ressource

KORREKTUR D-2 — §3.2 DECISIONLAMBDATREES PRO BAUSTEIN  (F-EXTRA-6)
================================================================================

WAS v3 SAGT
   "ENTSCHEIDUNGSKLASSEN (DecisionLambdaTree-Instanzen)
       - PageRelocationDecisionTree
       - PageTypeChangeDecisionTree
       - PrefetchAdjustmentDecisionTree
       - AllocatorRebalanceDecisionTree
       - ConcurrencyDisciplineSwitchDecisionTree
       - PageTypeSelectionDecisionTree
       - HotPathRecognitionDecisionTree
       - LayoutInvariantMaintenanceDecisionTree"
   (System-globale Trees, eine Instanz pro Entscheidungsklasse)

KORREKTUR v4
   DecisionLambdaTrees sind PRO BAUSTEIN definiert, nicht system-global.
   Jeder Baustein bringt die fuer ihn relevanten Trees mit. Ein Algorithmus
   = Komposition der Trees seiner gewaehlten Bausteine.

   BEISPIEL
     • ART_Node256-Baustein bringt:
         - PageRelocationTree (ART-spezifisch)
         - PageTypeChangeTree (ART → Node48 bei Schrumpfung)
     • AdaptivePrefetchDistance-Baustein bringt:
         - PrefetchAdjustmentTree (Khan-Style, P23)
     • HotPathRecognition-Baustein bringt:
         - HotPathRecognitionTree (Kuehn-Style, P28)
     • Wenn ein Algorithmus diese drei Bausteine nutzt:
         → Komposition: alle drei Trees aktiv

   KOMPOSITIONS-MECHANIK (C++23 Concepts + requires)
     template<typename Module>
     concept HasPageRelocationTree =
       requires(Module m) { { m.page_relocation_tree() } -> std::convertible_to<DecisionTree*>; };

     // Algorithmus-Modul aggregiert alle Trees seiner Bausteine
     class AlgorithmModule : public IAlgorithmStrategy<K,V> {
       std::vector<DecisionTree*> active_trees() const {
         std::vector<DecisionTree*> trees;
         if constexpr (HasPageRelocationTree<page_baustein>) trees.push_back(...);
         // ... pro Baustein
         return trees;
       }
     };

   QUELLE Bausteine_Matrix.txt — pro Bausteine-Eintrag die mitgebrachten
   DecisionTrees benannt.

KORREKTUR D-3 — §4.1 BUILDER-LIFECYCLE  (F-EXTRA-1, Compiler-Layering)
================================================================================

WAS v3 SAGT
   Builder-Lifecycle in 7 Phasen, Pre-Build per CMake-Skript.

ERGAENZUNG v4
   Phase "Adhoc Build" wird konkretisiert mit Compiler-Layering:

   ADHOC BUILD (KONKRETISIERT, F-EXTRA-1 + F-EXTRA-5)
     - Builder ruft `tools/permutation_codegen/codegen.py`
     - Skript erzeugt:
         a. Pro Permutation eine .cpp/.ccm Schalen-Datei (C++23)
         b. CMake-Targets (`add_library(perm_<flags> ...)`)
     - Skript erzeugt zusaetzlich pro Permutation eine
         `external_objects.cmake`-Liste, die die Original-Compiler-Object-
         Files referenziert.
     - Original-Compiler-Bausteine werden vorab kompiliert (siehe §6.3).
     - CMake linkt Schalen-.o + Original-Compiler-.o → ABI-stabiles Modul.

   COMPILER-LAYERING-PIPELINE
     1. Pre-Build-Phase verifiziert Verfuegbarkeit aller Original-Compiler-
        Versionen (F-EXTRA-1, Strategie A → B Fallback).
     2. Codegen erzeugt Schalen-Code (C++23) UND
        Bausteine-Wrapper-Code (Original-Compiler-kompatibel).
     3. Original-Compiler kompiliert seine Bausteine zu .o (intern visible).
     4. C++23-Hauptcompiler kompiliert die Schale zu .o (extern visible).
     5. Linker (kompatibel mit beiden ABIs) fasst alles zu .so/.dll/.dylib.

KORREKTUR D-4 — §4.2 PRE-BUILD-PIPELINE  (F-EXTRA-5)
================================================================================

WAS v3 SAGT
   "build_permutations.cmake (sequentiell pro Permutation)"

KORREKTUR v4
   Statt reines CMake → Python-Codegen-Skript erzeugt CMake-Targets,
   dann normaler CMake-Build (parallelisiert):

   `tools/permutation_codegen/codegen.py`
     - Liest Bausteine_Matrix + Flag_System
     - Enumeriert alle gueltigen Permutationen (ConstraintFilter)
     - Generiert pro Permutation:
         • Schalen-.cpp/.ccm (C++23-Modul-Wrapper)
         • CMake `add_library(perm_<flags> ...)`-Eintrag
     - Output: `build/generated/permutations.cmake`
   Hauptbuild includiert die generierte Datei und parallelisiert.

   BEGRUENDUNG (F-EXTRA-5 Empfehlung)
     CMake skaliert mit Hunderten Targets schlecht; Python-Codegen erzeugt
     klare CMake-Targets, die CMake dann effizient parallelisiert.

KORREKTUR D-5 — §4.5 MESS-MATRIX MIT DEFAULT+OVERRIDE  (F-EXTRA-7)
================================================================================

WAS v3 SAGT
   "Pro Zelle dieser Matrix existiert eine constexpr-spezialisierte
    Implementierung der Mess-Erfassung."

KORREKTUR v4
   Pro Zelle gibt es zwei Ebenen:
   • Default-Hook: generische Implementation pro Mess-Kategorie
   • Override: algorithmus-spezifische Spezialisierung (nur wo der
     Algorithmus etwas Spezifisches messen kann)

   KONZEPT-CONSTRAINT
     template<typename Algo, MeasurementCategory C>
     concept HasMeasurement =
       requires(Algo& a, Context& ctx) {
         { Measure<C, AlgorithmDetailOf<Algo>>::at_node_visit(a, ctx) };
       };

   FALLBACK-LOGIK
     template<typename Algo, MeasurementCategory C>
     constexpr void hooked_node_visit(Algo& a, Context& ctx) noexcept {
       if constexpr (HasMeasurement<Algo, C>) {
         Measure<C, AlgorithmDetailOf<Algo>>::at_node_visit(a, ctx);
       } else {
         // Default-Hook: generische Implementation
         GenericMeasure<C>::at_node_visit(a, ctx);
       }
     }

KORREKTUR D-6 — §6.3 ORIGINAL-COMPILER-PIPELINE  (F-EXTRA-1, KORRIGIERT)
================================================================================

WAS v3 SAGT
   "Jeder fremde Algorithmus wird mit SEINEM Original-Compiler kompiliert,
    mit dem das Originalpaper das Verhalten verifiziert hat."
   (Implizit: ganzes Modul mit Original-Compiler)

KORREKTUR v4 (KRITISCH)
   Hauptcompiler ist IMMER C++23. Nur die jeweiligen Bausteine
   (= Originalcode-Snippets aus den Papers) werden mit ihrem Original-
   Compiler kompiliert und anschliessend in unser C++23-Modul-Wrapper
   STATISCH GELINKT.

   ARCHITEKTUR-LAYERING (F-EXTRA-1)
     • Schale ("Modul-Wrapper")
         Compiler: C++23 (modern, GCC 14+ / Clang 17+ / MSVC 19.39+)
         Inhalt:   Adapter, Concept-Bindungen, ABI-stabiles Modul-Interface
         Sichtbarkeit: extern visible Symbol-Set (ABI)
     • Internals ("Originalcode-Bausteine")
         Compiler: Original-Compiler des jeweiligen Papers
         Inhalt:   exakter Originalcode (Habich-Direktive)
         Ausgabe:  .o (Object-File) oder .a (statische Library)
         Sichtbarkeit: intern (kein externes Symbol des Moduls)
     • Statisches Linking
         Beide Schichten werden zur Compile-Time des Moduls statisch
         gelinkt zu einem ABI-stabilen .so/.dll/.dylib.

   STRATEGIE FUER COMPILER-VERSIONS-FESTLEGUNG (F-EXTRA-1)
     A — Paper-Acknowledgement (Compiler-Version aus Originalpaper)
     B — GitHub-Repo (CI-Files / Dockerfiles)
     C — Email-Anfrage an Autoren (Fallback bei Unklarheit)
     Aktuelle Strategie: A → B Fallback. Phase 4.B konkretisiert pro Algo.

KORREKTUR D-10 — PERMUTATIONS-IDENTIFIER-SCHEMA  (F10-K)
================================================================================

WAS v3 SAGT
   "perm_id" als opake Hash/Tupel-String-ID.

KORREKTUR v4
   Permutations-Identifier ist ein strukturiertes Flag-System nach Vorbild
   der Intel-CPUID-Feature-Flags. Pro Bausteine-Achse eine `uint64_t`-Bank
   mit Bit-Positionen pro Implementation. Permutation = Vereinigung der
   gesetzten Flags.

   QUELLE Vollstaendige Bit-Belegung in `Flag_System.txt` (NEU).

   STRUCT
     struct PermutationFlags {
       std::uint64_t page_bank;
       std::uint64_t node_bank;
       std::uint64_t traversal_bank;
       std::uint64_t value_handle_bank;
       std::uint64_t memory_layout_bank;
       std::uint64_t allocator_bank;
       std::uint64_t prefetch_bank;
       std::uint64_t concurrency_bank;
       std::uint64_t isa_bank;
       constexpr std::string to_identifier() const noexcept;
     };

   IDENTIFIER-FORMAT (Beispiel)
     "PAGE_DENSEBYTE_ART256.NODE_NODE256.TRAVERSAL_BYTEBYBYTE.
      VALUEHANDLE_INLINE.MEMORY_CACHELINE_ALIGNED.ALLOCATOR_POOL_PER_PAGETYPE.
      PREFETCH_NONE.CONCURRENCY_OLC|MEMORY_READ_DISC.
      ISA_SCALAR_X86_64|X86_AVX512F|X86_BMI2"

   FOLGEN
     • CMake generiert pro Permutation ein menschen-lesbares Modul-File
     • ConstraintFilter wird zur Bit-Maskierung (Compile-Time)
     • Module sind eindeutig identifizierbar ohne Hash-Kollision
