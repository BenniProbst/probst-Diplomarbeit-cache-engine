1. ARCHITEKTUR-GRUNDPRINZIPIEN  (REV 3)
================================================================================

(A) BASISVERTRAG (unveraendert vs v2)
    Jeder Algorithmus implementiert die `std::map<Key,Value>`-API (C++23).
    Algorithmen sind dropin-Ersatz fuer `std::map`. Key-Type kann implizit
    mit Hashing/Fingerprinting ueberlagert sein.

(B) ENGINE-CHOICE (unveraendert vs v2)
    `template<typename Algo, typename EngineKind> Container<...>`
       • StaticEngine — Originalcode + Adapter; KEINE Optimierungen ueber
         State-of-the-Art hinaus.
       • CacheEngine  — aktive Optimierung; Visitor + Observer + Command-
         Lambda-Trees + ConcurrencyManager + constexpr-Telemetrie.
    Engine-Choice ist Compile-Time, KEIN Runtime-Switch.

(C) CACHE-ENGINE-LOKATION (KORRIGIERT F12)
    Die Cache Engine ist KEIN separates globales Singleton-Heap-Modul.
    Sie lebt IM `CacheEngineBuilder` (= main.cpp Orchestrator).
    Sie wird zwischen Modul-Experimenten zurueckgesetzt.
    Cache-Warmup gehoert ZUR Algorithmus-Permutation (nicht zur CacheEngine).

(D) ZWEI BETRIEBSMODI DES BUILDERS (KORRIGIERT F12)
    Schicht A — PERMUTATIONS-BUILD (vorbereitend, einmalig pro Plattform)
       - CMake-Skript baut alle gueltigen Permutationen als ABI-stabile
         C++23-Module.
       - Pro fremdem Algorithmus mit dessen Original-Compiler.
       - Pre-Build-Phase, dauert Stunden bis Tage, EINMALIG je Plattform.
    Schicht B — EXPERIMENT-AUSFUEHRUNG (Builder-Runtime)
       - CacheEngineBuilder (main.cpp) iteriert ueber pre-built Module.
       - Pro Modul: dynamisch laden, Cache-Warmup, Dataset-Prep, Experiment,
         Reset, Modul entladen.
       - In-Memory MeasurementBuffer akkumuliert; am Ende Disk-Dump + LaTeX.

(E) HABICH-DIREKTIVE (unveraendert vs v2)
    Originalcode aller fremden Algorithmen wird EXAKT KOPIERT uebernommen.
    Adapter-Pattern als Anbindung. Originalcode wird mit DEM ORIGINAL-COMPILER
    des Papers separat kompiliert (F7-Praezisierung). Invasive Eingriffe
    (Messpunkte) NUR mit Habich-Absprache.

(F) ZIELSTANDARD: C++23 (unveraendert)
    Module fuer ABI-Stabilitaet (F9). `requires`-Klauseln fuer Concepts.
    `constexpr` fuer Mess-Kategorien-Inlining (F1).

(G) READ COUNTER = uint64_t (unveraendert)

(H) MEMORY RECLAMATION = RCU (unveraendert; Hazard Pointers raus)

(I) MEASUREMENT IST IN-MEMORY (KORRIGIERT F5)
    Eigene einfache, effiziente In-Memory-Loesung. KEINE externe DB.
    Begruendung (Architekt): "Latenzen einer DB interferieren mit
    Experimenten. Wir koennen Kontrolle nicht an eine Time-Series-Datenbank
    abgeben, ohne den Cache und den Kernel zu unterbrechen."

(J) BAUSTEINE-QUER-PERMUTATION (NEU F15 — ZENTRALES PRINZIP)
    Jeder Algorithmus-Baustein (Page-Type, Node-Type, Traversal, ValueHandle-
    Strategy, MemoryLayout, Allocator, Prefetch, Concurrency-Disziplin) ist
    EINZELN gegen einen anderen aus JEDEM BELIEBIGEN anderen Algorithmus
    AUSTAUSCHBAR. Untersuchung jedes einzelnen Prinzips gegen jedes Andere.
    Die Cache Engine zeigt ihren massgeblichen Einfluss auf ALLE Bausteine.

(K) KONZEPT-MAPPING (unveraendert vs v2)
    Konzeptionelle Elemente als C++23 Concepts mit `requires`-Klauseln:
       FanOutContainer, Page, Node, Traversal, MemoryLayout,
       ValueHandleStrategy, PageAllocator, PrefetchStrategy,
       ConcurrencyDiscipline, Telemetry, MeasurementCategory.

3. DOMAENE 1 — SEARCH ENGINE  (REV 3)
================================================================================

(Strukturell unveraendert vs v2 §3 — `fan_out_engine`, Algorithm Strategies,

3.1 ALGORITHMUS-MODULE ALS C++23 ABI-STABILE MODULE  (F9)
   • Jede Permutation der Bausteine (Page x Node x Traversal x ... x ISA)
     wird als eigenes ABI-stabiles C++23-Modul gebaut.
   • Module werden VOR dem Builder-Lauf via CMake-Skript pre-built.
   • Builder laed sie zur Laufzeit dynamisch (`dlopen` / `LoadLibrary`).
   • Modul-Schnittstelle:
        export module comdare.algo_perm.<perm_id>;
        export class AlgorithmModule : public IAlgorithmStrategy<K,V> {
          ...
        };

3.2 OBSERVER-PUSH + COMMAND-LAMBDA-TREES  (F2)
   • Algorithmus implementiert `IObserverProducer`; bei Hot-Path-Ereignissen
     ruft direkt `runtime.notify(event)` synchron auf.
   • Pro Entscheidungsklasse haelt CacheEngine eine `DecisionLambdaTree`-
     Instanz. Tree entscheidet:
        - EXECUTE (Anpassung sofort)
        - DELAY   (Anpassung verschieben → Barriere/Konsolidierung)
        - SKIP    (Anpassung ueberspringen)
   • Komponente:
        template<typename EventT>
        class DecisionLambdaTree {
          using Decision = enum class { EXECUTE, DELAY, SKIP };
          // konfigurierbare Lambda-Knoten
          constexpr Decision evaluate(EventT&&, Context&) const noexcept;
        };

   ENTSCHEIDUNGSKLASSEN (DecisionLambdaTree-Instanzen)
     - PageRelocationDecisionTree
     - PageTypeChangeDecisionTree
     - PrefetchAdjustmentDecisionTree
     - AllocatorRebalanceDecisionTree
     - ConcurrencyDisciplineSwitchDecisionTree
     - PageTypeSelectionDecisionTree
     - HotPathRecognitionDecisionTree
     - LayoutInvariantMaintenanceDecisionTree

   FORSCHUNGS-BELEGE FUER BARRIEREN/DELAYS
     • P02 HOT — Compound-Node-Konsolidierung als Barriere
     • P03 Masstree — Permutation-Field aktualisiert ohne Move
     • P05 START — Rewiring laeuft mit Barrieren
     • P08 ARTSync — OLC deferred Updates via Lock Coupling
     • P18 Saikkonen — Multi-Level Reloc periodisch
     • P28 Kuehn — Histogram-Update inkrementell, Re-Layout ausgeschlossen
     • P29 RCU — Grace Period als explizite Barriere
     • P26 Zhang FGCS — Hot-Path-Detection erst nach Threshold

3.3 VISITOR-MID-GRANULARITAET  (F3)
   • CacheEngine ruft `accept(visitor)` am Algorithmus auf
   • Visitor kennt nur:
        + visit(IPage*)
        + visit(INode*)
   • KEINE feinere Granularitaet (kein visit(ValueHandle*)/visit(TraversalStep*))
   • Respektiert Habich-Direktive (Originalcode-Boundary)

3.4 VALUEHANDLE: std::variant + Concept-Constraint  (F8)
   class ValueHandle {
     std::variant<InlineHandle, PointerHandle, RedirectToNodeHandle,
                  RedirectToPageHandle, DynamicHandle> v_;
   };
   template<ValueHandleKind K, typename AlgoTag>
   concept AllowedHandle = ...;   // begrenzt erlaubte Varianten je Algo
   template<typename Algo>
     requires AllowedHandle<DynamicHandle, AlgoTag<Algo>>
   class DynamicHandle { ... };

3.5 CONCURRENCYMANAGER: Klassen + Policy-Template  (F6)
   • 8+ Disziplin-Klassen (PageConcurrency, NodeConcurrency, ...)
     als Base-Implementierungen
   • Top-Level: `template<typename... Ds> class ConcurrencyManager`
     komponiert Disziplinen zero-overhead compile-time.
   • Singleton-Mechanik wie CacheEngine (heap, unique_ptr + call_once).

4. DOMAENE 2 — CACHE ENGINE & BUILDER  (KOMPLETT NEU STRUKTURIERT, F12)
================================================================================

4.1 OBERSTE EINHEIT: CacheEngineBuilder  (= main.cpp Orchestrator)
   ROLLE
     Eigenstaendiges C++23-Programm pro ISA-Plattform. Aus Source kompiliert
     mit den Plattform-spezifischen Compiler-Versionen (selbst gebaut auf
     Pi 5 / VisionFive 2; cross-compiled fuer ZIH-Lieferung).
     Beinhaltet die CacheEngine als Komponente.

   LEBENSZYKLUS (Phase fuer Phase)
     1. PLATFORM-PROBE
        - CPU-Features (ISA, Hybrid-Cores, Cache-Topo, Memory-Topo)
        - Verfuegbare Compiler-Versionen pro fremdem Algorithmus
        - Initialisiert LiveCpuModel
     2. MODE-DETECTION
        - Compile-Time-Modus (Default) ODER Runtime-Modus (ZIH) — gegenseitig
          ausschliessend
     3. MODULE-PERMUTATIONS-SCAN
        - Scan `build/modules/` nach pre-built Modulen
        - Ergebnis: Liste vorhandener / fehlender Permutationen
     4. ADHOC BUILD (nur falls fehlend)
        - Ruf `build_permutations.cmake` mit Liste fehlender perm_ids
        - Sequentieller Bau pro Permutation, jeweils mit dem fuer den
          Fremd-Algorithmus passenden Original-Compiler
     5. EXPERIMENT-LOOP (pro Modul)
        a. CacheEngine.reset()
        b. Modul dynamisch laden
        c. Cache-Warmup (modul-spezifisch, gehoert zur Permutation)
        d. Dataset-Aufbereitung
        e. Experiment ausfuehren
              - perf/PAPI Makro-Messung
              - Interne Mikrobenchmarks (continuous im Builder-Modus)
              - constexpr-Telemetrie pro (MessKategorie x AlgoDetail)
        f. Push observations → CacheEngine via Observer
        g. CacheEngine evaluiert DecisionLambdaTrees → EXECUTE/DELAY/SKIP
        h. Messungen → InMemoryMeasurementBuffer
        i. Modul entladen
     6. SERIALISIERUNG
        - InMemoryMeasurementBuffer → Disk-Dump (Binary/CSV)
     7. LATEX-RENDERING
        - LatexRenderer liest Disk-Dump, generiert Anhang fuer Diplomarbeit

4.2 PERMUTATIONS-BUILD-PIPELINE  (F10)
   build_permutations.cmake (sequentiell pro Permutation)
     1. Codegen — Template-instanziierter .cpp + .ccm Modul-Interface
     2. Compile mit Original-Compiler des jeweiligen Fremd-Algorithmus
        (Habich-Direktive, F7)
     3. Link zu ABI-stabilem Modul (.so / .dll / .dylib)
     4. Output: `build/modules/<perm_id>/<perm_id>.module.so`

   PRAEZISIERUNG (F4)
     • Permutationsraum vollstaendig
     • ISA-Filter via CMake compile-time
     • ConstraintFilter sortiert absurde Kombis aus
     • Cross-Compile-Toolchains pro Target im CMake hinterlegt
     • Pro fremdem Algorithmus: dessen Original-Compiler-Version registriert

4.5 MESS-KATEGORIE × ALGORITHMUS-DETAIL MATRIX  (F1, ZENTRAL)

   struct Measure {

     }
   };

   template<>
   struct Measure<cm::Category::CLU, ad::Detail::HOT_CompoundNode> {
     static constexpr void at_node_visit(...) noexcept {
       // HOT-spezifische CLU-Messung (Bit-Granularitaet beachten)
     }
   };

   template<>
   struct Measure<cm::Category::dTLB, ad::Detail::ART_Node256> { ... };
   template<>
   struct Measure<cm::Category::dTLB, ad::Detail::HOT_CompoundNode> { ... };
   ...

   ZUORDNUNG via C++23 Concepts + requires:
   template<typename Algo, cm::Category C>
     requires cm::HasMeasurement<Algo, C>
   constexpr void hooked_node_visit(Algo& a, Context& ctx) {
     Measure<C, ad::DetailOf<Algo>>::at_node_visit(a, ctx);
   }

   FOLGEN

     • Pro Algorithmus-Modul wird ein bestimmtes Mess-Set ge-inlined

9. SCHNITTSTELLE SEARCH-ENGINE ↔ CACHE-ENGINE  (REV 3)
================================================================================

OBSERVER (Algorithmus → CacheEngine, Push synchron mit Lambda-Tree-Filter)
   Algorithmus implementiert IObserverProducer; ruft direkt
   `runtime.notify(event)` synchron auf. Cache-Engine evaluiert pro
   Event den passenden DecisionLambdaTree → EXECUTE/DELAY/SKIP.

   EVENTS (vorlaeufig)
     • PageAccessed         (page_handle, branch_taken)
     • NodeAccessed         (node_handle, child_idx)
     • PathTraversed        (path_signature, depth, terminal_kind)
     • TelemetryUpdate      (page_handle, telemetry_delta)
     • MutationCommitted    (op_kind, count)
     • ConsolidationBarrier (barrier_id)              [P02 / P05 / P29]
     • GracePeriodElapsed   (gp_id)                   [P29 RCU]

VISITOR (CacheEngine → Algorithmus, Mid-Granularitaet)
   • visit(IPage*)
   • visit(INode*)

EMPFEHLUNG (CacheEngine → Algorithmus)
   • CacheEngine empfiehlt Strategie aus CompileTimeKnowledge
   • Algorithmus uebernimmt oder ignoriert (im Zweifel: statisch
     ausgelieferte optimale Variante laufen)

VERBOTEN
   • CacheEngine darf NICHT Algorithmus-Internals direkt manipulieren
   • Algorithmus darf NICHT die CacheEngine-Internals umgehen
   • Engine-Choice ist Compile-Time, KEIN Runtime-Switch
