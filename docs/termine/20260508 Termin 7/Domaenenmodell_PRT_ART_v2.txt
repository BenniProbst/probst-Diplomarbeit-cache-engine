1. ARCHITEKTUR-GRUNDPRINZIPIEN
================================================================================

(A) BASISVERTRAG
   Jeder Such-Algorithmus implementiert die `std::map<Key, Value>`-API
   (vollstaendig, C++23). Algorithmen sind dropin-Ersatz fuer std::map.
   Der Key-Type kann implizit mit Hashing/Fingerprinting ueberlagert sein
   (z.B. fuer ART/HOT-Style Bit-Manipulation auf bytewise-Schluesseln).

(B) ENGINE-TYPE-WAHL
   Jeder Algorithmus existiert in zwei Engine-Varianten, gewaehlt ueber Template-
   Parameter:
     • `StaticEngine<Algo>`  — exakter Originalcode + Adapter; KEINE
        Optimierungen ueber State-of-the-Art hinaus
     • `CacheEngine<Algo>`   — aktive Optimierung; Compile-Time-Permutation +
        Runtime-Visitor/Observer + ConcurrencyManager + Mikrobenchmarks
   Beide liefern Mikrobenchmarks; nur CacheEngine optimiert aktiv.

(C) ZWEI FUNKTIONSSCHICHTEN DER CACHE ENGINE
   Schicht 1 — COMPILE TIME (Programm: `CacheEngineBuilder`)
     - Permutiert Algorithmus-Bestandteile (Page-Type x Node-Layout x
       Traversal x ValueHandle-Strategy x Allocator x Concurrency-Disziplin
       x ISA-Pfad x ...) gegeneinander
     - C++23-Metaprogrammierung: statische Kompilation jeder Permutation
     - Misst Permutationen (Cache-Warmup, Datensatz-Aufbereitung, Benchmark)
     - Persistiert in Datenbank
     - Rendert finalen LaTeX-Anhang fuer die Diplomarbeit (Tabellen, Plots)
   Schicht 2 — RUNTIME (Globales Heap-Modul, Singleton-aehnlich)
     - Observer Pattern: Algorithmus benachrichtigt Cache Engine ueber Zustand
     - Visitor Pattern: Cache Engine besucht Algorithmus-Knoten zur Laufzeit
     - Empfiehlt Ausfuehrungsstrategie (basierend auf Compile-Time-Wissen)
     - Fuehrt zu statischer Auslieferung der gewaehlten/optimalen Strategie
       je Architektur (per kompilierter Variante geladen)
     - Echtzeit-Mikrobenchmarks akkumulieren im Speicher, werden gespoolt
     - ConcurrencyManager-Singleton lebt in der CacheEngine

(D) CACHE ENGINE = LAUFENDES CPU-MODELL
   Per Definition ein laufendes Modell der CPU, ihrer Eigenschaften, Prozesse/
   Ablaeufe und Verarbeitungs-Bewusstsein, um Verarbeitungseigenschaften mit
   wissenden Entscheidungen ueber die Architektur zu verbessern.

(E) HABICH-DIREKTIVE (Originalcode unangetastet)
   - Originalcode JEDES fremden Algorithmus (P01-P33 ausser PRT-ART) wird
     EXAKT KOPIERT uebernommen.
   - Anbindung erfolgt ueber ein Adapter-Pattern.
   - Einzelne invasive Eingriffe (z.B. Messpunkt-Hooks) muessen mit Prof. Habich
     ABGESPROCHEN werden — bis dahin nur extern messen.
   - PRT-ART (eigener Test-Algorithmus) ist die einzige Ausnahme, in die wir
     frei eingreifen duerfen.

(F) KONZEPT-MAPPING (Klassen ↔ C++ concepts)
   Konzeptionelle Elemente werden als C++ concepts mit `requires`-Klauseln
   modelliert. Jeder Algorithmus liefert pro konzeptionellem Element seine
   eigene Implementierung — alle erfuellen dasselbe Interface (Concept).
   Konzeptionelle Elemente:
     • Page                (Suchseite)
     • Node                (Knoten)
     • Traversal           (Lookup-Pfad-Strategie)
     • MemoryLayout        (Allocation + Alignment fuer Nodes/Data/Inline/Meta)
     • ValueHandleStrategy (Inline | Pointer | RedirectToNode/Page)
     • PageAllocator       (Pool/Arena/Slab)
     • PrefetchStrategy
     • ConcurrencyDiscipline
     • Telemetry

(G) ZIELSTANDARD: C++23
   - Verbesserte Metaprogrammierung (constexpr, concepts, deducing this)
   - ABI-stabile Module fuer Algorithmus-Austausch ueber gleiches Interface
   - Erleichtert die globale Messung aller Experimente durch CacheEngineBuilder.

(H) READ COUNTER = uint64_t
   Aufgrund von Langzeit-Experimenten (Stunden bis Tage) sind Read Counter
   pro Block/Knoten als `std::uint64_t` zu modellieren (KEIN u32).

(I) MEMORY RECLAMATION
   - RCU als Default fuer Online-Relocation (P29 McKenney 2001)
   - Hazard Pointers RAUS — memory leak ist verbotenes undefiniertes Verhalten,
     Aufraeumen ist Pflicht. Deterministische Reclamation in Verbindung mit
     RCU/EpochManager.
   - Kein GPU-Code (CPU-only Scope der Diplomarbeit).

3.5 PACKAGE: value_handle (KORRIGIERT v2 — Sache der Node)
================================================================================

ValueHandle ist eine Eigenschaft DER NODE. Zur Compile-Time begrenzt ein
`switch_array<ValueHandleKind, ...>` die zulaessigen Varianten je Algorithmus.
Zur Runtime waehlt der Algorithmus je nach Knoten-Eigenschaften (Wertegroesse,
Hot/Cold, Pointer-Tiefe, ...) die konkrete Variante.

CONCEPT ValueHandleStrategy<S, V>                                  [C++23 CONCEPT]
   requires {
     { s.kind() } -> std::same_as<ValueHandleKind>;
     { s.resolve() } -> std::same_as<V*>;
     { s.is_inline() } -> std::same_as<bool>;
   };

ENUM ValueHandleKind {
     Inline,                  // Wert direkt in Node-Slot
     Pointer,                 // External Pointer
     RedirectToNode,          // Redirect-Knoten (analog Patricia/Macro)
     RedirectToPage,          // Redirect-Page
     ChainRef,                // VERTAGT: Wertekette
     Dynamic                  // Runtime-Auswahl (mit switch_array begrenzt)
};

CLASS InlineValueHandle implements ValueHandleStrategy
CLASS PointerValueHandle implements ValueHandleStrategy
CLASS RedirectToNodeValueHandle implements ValueHandleStrategy
CLASS RedirectToPageValueHandle implements ValueHandleStrategy
CLASS DynamicValueHandle implements ValueHandleStrategy
   - allowed_kinds: std::array<ValueHandleKind, N>     (compile-time begrenzt)
   - resolved_kind: ValueHandleKind                    (runtime-gewaehlt)
   - select_at_runtime(NodeContext) -> ValueHandleKind

NOTE Die compile-time-`switch_array` ist ein constexpr-Array, das je
Algorithmus die zulaessigen Varianten kodiert. Beispiel:
   ART:        Inline | Pointer | RedirectToNode
   HOT:        Inline | Pointer
   B²-tree:    Inline | Pointer | RedirectToPage
   PRT-ART:    Inline | Pointer | RedirectToNode | RedirectToPage | Dynamic

================================================================================

ROLLE
   Globales Heap-Modul (Singleton-aehnlich), das per Observer-Pattern
   Telemetrie von Such-Algorithmen empfaengt und per Visitor-Pattern
   Such-Algorithmus-Strukturen besucht. Empfiehlt Ausfuehrungsstrategien

   - telemetry_spool: TelemetrySpool

   + visit(IAlgorithmStrategy*)
   + on_observation(ObservationEvent)

9. SCHNITTSTELLE SEARCH-ENGINE ↔ CACHE-ENGINE  (NEU v2)
================================================================================

OBSERVER-RICHTUNG (Algorithmus → CacheEngine)
   - Algorithmus implementiert IObserverProducer; ruft notify(...) bei
     wesentlichen Ereignissen auf:
       • PageAccessed        (page_handle, branch_taken)
       • NodeAccessed        (node_handle, child_idx)
       • PathTraversed       (path_signature, depth, terminal_kind)
       • TelemetryUpdate     (page_handle, telemetry_delta)
       • MutationCommitted   (op_kind, count)

VISITOR-RICHTUNG (CacheEngine → Algorithmus)
   - CacheEngine ruft accept(visitor) am Algorithmus auf; Visitor besucht
     Page/Node/Traversal-Strukturen ueber Concept-Interfaces, OHNE algorithmus-
     spezifische Internals zu kennen:
       • visit(IPage*)
       • visit(INode*)
       • visit(ITraversal*)

EMPFEHLUNG-RICHTUNG (CacheEngine → Algorithmus)
   - CacheEngine empfiehlt Strategie (basierend auf CompileTimeKnowledge);
     Algorithmus kann Empfehlung uebernehmen oder ignorieren (im Zweifel:
     statisch ausgelieferte optimale Variante laufen lassen).

WAS VERBOTEN IST
   - CacheEngine darf NICHT Algorithmus-Internals direkt manipulieren.
   - Algorithmus darf NICHT die CacheEngine-Internals umgehen
     (z.B. eigenen ConcurrencyManager parallel betreiben).
   - Engine-Choice (Static vs Cache) ist Compile-Time, KEIN Runtime-Switch.
